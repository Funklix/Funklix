|---|---|

## Findings

- The Activity Feed static shell uses `#activity-panel`, `#activity-toggle-btn`, `#activity-count`, and `#activity-feed`.
- Entries are generated dynamically by `renderActivityFeed()` with `.activity-entry`, `.activity-avatar`, `.activity-body`, and `.activity-new-label` classes.
- Unread state is controlled by `updateActivityUnreadIndicator()`, which toggles `.has-unread` and updates `#activity-count` text.
- Collapse/expand behavior is controlled by the existing `#activity-toggle-btn` listener and `state.activityCollapsed`.
- Clickable entries receive `role="button"`, `tabIndex = 0`, click, and keyboard handlers in `renderActivityFeed()`.
- Runtime behavior is class/ID sensitive, so PR 1 should not modify `app.js` or generated entry logic.

## Safest migration strategy

- Add `.fk-section` to the static Activity container.
- Add `.fk-btn .fk-btn-ghost` to the static Activity toggle.
- Add `.fk-badge` to the static unread count.
- Keep dynamic classes generated by `app.js` unchanged.
- Use CSS only to polish `.activity-entry`, `.activity-avatar`, `.activity-body`, `.activity-new-label`, hover/focus, empty state, and spacing.
- Preserve all IDs, event listeners, generated class names, collapse behavior, unread behavior, and node-focus behavior.

## Low-risk PR 1 scope

- Activity container surface and spacing.
- Header/toggle visual polish.
- Unread count badge polish.
- Empty state polish.
- Activity entry card styling through existing `.activity-entry` CSS.
- Avatar, timestamp, typography, hover, focus-visible, and unread card styling.

## Deferred / legacy areas

- No `app.js` class generation changes.
- No change to activity types, labels, timestamps, unread detection, localStorage seen-state, node focusing, keyboard behavior, or persistence.
- No sidebar navigation changes.
- No Activity Feed data model changes.

## Blast radius

Low. Static class additions in `index.html`, scoped Activity CSS updates in `styles.css`, and this audit file. No runtime code changes are required.

## Decision

Proceed with PR 1 immediately because the migration is low risk and can remain visual-only without touching `app.js`.
