## Executive Summary

Funklix is moving from editable Brand fields toward a **Marketing Knowledge Operating System**. The current Brand Workspace already contains useful building blocks: board-scoped Brand Core state, built-in strategic fields, custom tiles, contextual Missing Knowledge prompts, Brand DNA, Brand Avatar, Brand Assets, website analysis, Dashboard Brand Evolution signals, and save/load serialization into board state.

However, specialized knowledge areas such as **Founder Story**, **Market Research**, **Pitch Deck**, **Whitepaper**, and **Business Plan** are currently represented as lightweight Custom Brand Tiles. That is safe for setup shortcuts, but it is not enough for the future product vision. These areas will eventually need richer lifecycle support: identity, metadata, source material, attachments, AI actions, review state, history, readiness, search, and graph relationships.

This audit recommends introducing a reusable **Knowledge Module** architecture before implementing specialized modules. The architecture should let every module share a common lifecycle while allowing each module type to opt into only the capabilities it needs.

This PR is documentation only. It does not implement modules, uploads, research, AI actions, APIs, save/load changes, board snapshot changes, Brand Core state changes, or UI changes.

## Current Architecture

### Current Brand Core data

Current Brand Core state is a board-scoped object with built-in fields and a `customTiles` array. The default shape includes:

- `brandCore`
- `toneOfVoice`
- `messagingPillars`
- `valueProposition`
- `personas`
- `contentGuidelines`
- `dosAndDonts`
- `brandVoiceExamples`
- `keywords`
- `brandAssets`
- `brandDNA`
- `customTiles`

The model is practical and lightweight, but it combines several future concepts:

- Brand identity
- Strategy
- Voice
- Deployment assets
- Knowledge references
- AI-derived Brand DNA
- Custom user knowledge

### Current custom tiles

Custom tiles currently live in:

```js
state.brandCore.customTiles
```

Existing custom tile shape is effectively:

```js
{
  title: string,
  content: string,
  items?: array
}
```

Current identity is presentation-based and index-derived:

```text
custom:{index}
```

Custom tiles do not currently have:

- stable persisted IDs
- module type
- status
- review state
- source metadata
- attachments
- provenance
- history
- readiness
- action registry
- graph relationships
- persisted section/category metadata

The actionable Missing Knowledge flow safely creates or selects Custom Brand Tiles with canonical titles, but it intentionally avoids adding a new schema.

### Current rendering pipeline

Brand Workspace rendering is currently driven by `renderBrandCoreTiles()`.

Current rendering responsibilities include:

1. rendering the Brand Workspace hero and grouped sections
2. rendering Brand DNA card state
3. refreshing contextual Missing Knowledge blocks
4. removing stale custom tile DOM
5. rendering built-in `.bc-node[data-bc-key]` cards
6. rendering custom tiles either in mapped sections or Custom Knowledge
7. rendering the `custom:add` card

This rendering path works for current fields, but specialized modules will need a clearer separation between:

- module registry
- module list/querying
- module card renderer
- module editor renderer
- module action renderer
- persistence serializer

### Current editor

The existing editor is generated by `renderBrandCoreEditor()` based on `state.brandCoreSelectedKey`.

Current editor modes include:

- scalar text fields such as Brand Core and Value Proposition
- arrays such as Tone of Voice, Messaging Pillars, Content Guidelines, Keywords
- structured objects such as Brand Assets, Do/Don't Rules, Brand Voice Examples
- personas array editor
- custom tile editor keyed by `custom:{index}`

The editor is functional but does not yet model specialized module editors. A future Market Research editor, for example, may need research questions, findings, sources, competitor notes, confidence, AI actions, and review state. A Pitch Deck module may need attachment metadata, extraction status, slide summaries, and proof points. These are too large for a generic title/content custom tile editor.

### Current persistence

Brand Core state is normalized, serialized, and persisted through the existing Brand Brain persistence flow.

Current persistence characteristics:

- board-scoped Brand Core state
- local Brand Brain storage path
- board snapshot serialization through `brand_core_snapshot`
- no independent Workspace-level Brand entity yet
- no module-specific persistence table or API
- no attachment persistence
- no history/audit event persistence

This is intentionally lightweight and should remain untouched until a dedicated implementation PR designs the storage and migration path.

### Current section grouping

Current visual grouping is:

| Section | Current purpose |
|---|---|
| Foundation | Brand Core / identity, mission, vision, values framing |
| Strategy | Value Proposition, Personas / ICP, Messaging Pillars, Tone of Voice |
| Intelligence | Brand DNA, Brand Avatar, knowledge and website analysis framing |
| Deployment | Brand Assets, Keywords, Content Guidelines, Do/Don't Rules, Voice Examples |
| Custom Knowledge | User-created Custom Brand Tiles |

Canonical Missing Knowledge tiles are visually placed by title:

| Canonical tile | Current visual section |
|---|---|
| Founder Story | Intelligence |
| Market Research | Strategy |
| Business Plan | Strategy |
| Pitch Deck | Deployment |
| Whitepaper | Deployment |

This title-based placement is a safe transitional approach, not a long-term module architecture.

## Problems

### 1. Custom tiles are doing too much

Custom tiles are being used for both freeform user notes and future strategic knowledge modules. That keeps runtime risk low today, but it will not scale to modules that need status, attachments, source tracking, AI actions, history, and readiness.

### 2. Index-based identity is not enough for modules

The current `custom:{index}` identity is acceptable for lightweight tiles but unsafe for richer module lifecycles. Future modules need stable IDs because they may have attachments, history entries, review decisions, search indexes, graph edges, and async AI jobs.

### 3. Section placement is title-derived

The current mapping places canonical missing-knowledge tiles in sections by title. That avoids schema changes but cannot support renamed modules, multiple modules of the same type, workspace-level modules, or module status views.

### 4. No module lifecycle exists

Current custom tiles move directly from missing prompt to editable title/content tile. Future modules need lifecycle concepts such as:

- not started
- draft
- importing
- analyzing
- needs review
- approved
- stale
- archived

### 5. No capability model exists

Not every module should support uploads, AI actions, review, history, or graph publishing. The system needs explicit capabilities instead of one large module shape that forces every module to carry every future field.

### 6. No provenance model exists

Future knowledge should distinguish between:

- user-entered knowledge
- uploaded source material
- extracted summaries
- AI-generated suggestions
- approved Brand truth
- stale or superseded facts

### 7. No Knowledge Graph boundary exists

Brand Workspace currently stores fields and tiles, but does not distinguish raw input, reviewed knowledge, graph-ready facts, and campaign-consumable context.

## Target Architecture

### Knowledge Module

A **Knowledge Module** is a reusable container for one area of Brand or Marketing knowledge. It should support a common lifecycle and optional capabilities.

Recommended conceptual shape:

```ts
type KnowledgeModule = {
  id: string;
  type: KnowledgeModuleTypeId;
  title: string;
  section: "foundation" | "strategy" | "intelligence" | "deployment" | "custom";
  status: KnowledgeModuleStatus;
  readiness?: KnowledgeReadinessSummary;
  metadata?: KnowledgeModuleMetadata;
  knowledge?: KnowledgeContent;
  attachments?: KnowledgeAttachment[];
  actions?: KnowledgeModuleActionState[];
  history?: KnowledgeModuleHistoryEntry[];
  review?: KnowledgeReviewState;
  graph?: KnowledgeGraphProjection;
  createdAt: string;
  updatedAt: string;
};
```

This is a target architecture, not an implementation requirement for the current Brand Core state.

### Knowledge Module Type

A **Knowledge Module Type** describes what a module is and what it can do.

Recommended conceptual shape:

```ts
type KnowledgeModuleType = {
  id: string;
  label: string;
  description: string;
  defaultSection: string;
  defaultTitle: string;
  capabilities: KnowledgeModuleCapabilities;
  fields?: KnowledgeFieldDefinition[];
  supportedAttachments?: AttachmentKind[];
  aiActions?: KnowledgeAiActionDefinition[];
  readinessRules?: KnowledgeReadinessRule[];
  graphMapping?: KnowledgeGraphMapping;
};
```

Examples:

- `founder_story`
- `market_research`
- `pitch_deck`
- `whitepaper`
- `business_plan`
- `brand_assets`
- `custom_note`

### Knowledge Module Registry

The **Knowledge Module Registry** should be a single source of truth for available module types and their capabilities.

Responsibilities:

- define supported module types
- define default section placement
- define display labels and descriptions
- define optional capabilities
- define editor/renderer selection
- define future AI actions
- define upload support
- define graph export behavior

The registry prevents scattered hardcoded mapping logic as modules grow.

### Module Renderer

The **Module Renderer** displays a module card or section surface.

Responsibilities:

- render identity and status
- render readiness summary
- render last updated/provenance hints
- render attachment count if supported
- render review state if supported
- render primary/secondary actions based on capabilities
- respect section placement

It should not directly own persistence or AI execution.

### Module Editor

The **Module Editor** edits module-specific content while preserving shared editor patterns.

Responsibilities:

- render module-specific fields
- render source/attachment panes where supported
- render review controls where supported
- render AI action outputs where supported
- validate required knowledge fields
- save through existing/future module persistence service

A future editor should support both:

- generic modules such as Custom Note
- specialized modules such as Market Research or Pitch Deck

### Module Actions

Module actions should be declarative and capability-driven.

Example action categories:

| Action category | Examples | Notes |
|---|---|---|
| Setup | Create module, add source, add notes | User-driven structure only |
| AI | Summarize, extract insights, compare competitors | Future only; never implicit |
| Upload | Attach PDF, replace source file, remove source | Future only |
| Review | Mark reviewed, approve, reject, request changes | Needed before graph publishing |
| Publish | Publish to Knowledge Graph, use in campaign context | Future architecture step |
| Maintenance | Archive, duplicate, refresh analysis | Future |

### Module Metadata

Metadata should remain separate from knowledge content.

Recommended metadata categories:

- owner / creator
- source type
- source URL or file reference
- created/updated timestamps
- confidence
- language
- region/market
- audience segment
- document date
- review owner
- source freshness
- tags

Metadata should not be confused with approved Brand truth.

### Module Capabilities

Capabilities let modules opt into features independently.

Recommended capability flags:

```ts
type KnowledgeModuleCapabilities = {
  editableText?: boolean;
  structuredFields?: boolean;
  attachments?: boolean;
  aiActions?: boolean;
  reviewWorkflow?: boolean;
  readiness?: boolean;
  history?: boolean;
  graphProjection?: boolean;
  searchIndexing?: boolean;
  multiSource?: boolean;
  citations?: boolean;
};
```

Example capability matrix:

| Module type | Text | Structured fields | Attachments | AI actions | Review | Graph | Search |
|---|---:|---:|---:|---:|---:|---:|---:|
| Founder Story | Yes | Optional | Optional | Future | Yes | Yes | Yes |
| Market Research | Yes | Yes | Future | Future | Yes | Yes | Yes |
| Pitch Deck | Yes | Optional | Yes | Future | Yes | Yes | Yes |
| Whitepaper | Yes | Optional | Yes | Future | Yes | Yes | Yes |
| Business Plan | Yes | Yes | Future | Future | Yes | Yes | Yes |
| Brand Assets | Yes | Yes | Yes | Future | Optional | Yes | Yes |
| Custom Note | Yes | No | Optional | No by default | Optional | Optional | Yes |

## Module Lifecycle

Recommended lifecycle:

1. **Available** — module type exists in registry.
2. **Suggested** — module is recommended because knowledge is missing.
3. **Created** — module instance exists with stable ID and type.
4. **Draft** — user has started adding knowledge.
5. **Sourced** — module has source material or attachments, if supported.
6. **Analyzing** — future AI or parsing action is running.
7. **Needs review** — AI/user-added knowledge needs human review.
8. **Approved** — module content is accepted as usable Brand knowledge.
9. **Published** — approved knowledge is projected into Marketing Knowledge Graph / campaign context.
10. **Stale** — source or market assumptions may need refresh.
11. **Archived** — module remains in history but is not active context.

Not every module needs every lifecycle state. The registry should define which states are relevant.

## Future AI Integration

AI integration should be module-aware and action-specific, not a generic hidden generation pass.

Recommended principles:

1. **Explicit user action** — AI should run only when the user asks.
2. **Module-scoped context** — each AI action reads only the module, selected Brand context, and approved sources needed for that task.
3. **Draft outputs** — AI output should be saved as draft/suggestion until reviewed.
4. **Provenance preserved** — AI-derived claims should point back to sources where possible.
5. **No silent Brand truth** — AI output should not automatically become approved Brand knowledge.
6. **Capability-gated actions** — only modules that declare AI support should show AI actions.

Example future AI actions:

| Module | Future AI action |
|---|---|
| Founder Story | Extract narrative angles, summarize founder credibility |
| Market Research | Summarize market trends, identify customer pains, compare competitors |
| Pitch Deck | Extract proof points, summarize slides, identify claims |
| Whitepaper | Summarize claims, extract terminology, identify citations |
| Business Plan | Extract GTM assumptions, identify risks, summarize business model |

## Future Upload Integration

Uploads should be module-scoped and metadata-rich.

Recommended principles:

1. Attachments belong to a module instance.
2. Attachment records store metadata separately from extracted knowledge.
3. Parsing/extraction is an explicit future action.
4. Source file presence does not equal approved Brand truth.
5. Deleting an attachment should not automatically delete reviewed knowledge unless explicitly designed.

Recommended attachment concepts:

```ts
type KnowledgeAttachment = {
  id: string;
  moduleId: string;
  kind: "pdf" | "image" | "doc" | "link" | "text";
  name: string;
  url?: string;
  storageRef?: string;
  mimeType?: string;
  sizeBytes?: number;
  uploadedAt: string;
  parseStatus?: "not_started" | "queued" | "parsed" | "failed";
};
```

No upload implementation should happen until a dedicated storage, security, file-size, retention, and parsing audit is complete.

## Future Search Integration

Knowledge Modules should eventually be searchable by:

- module title
- module type
- approved knowledge
- draft knowledge
- source metadata
- tags
- audience/market metadata
- attachment names
- extracted summaries

Recommended phases:

1. local client-side search over modules
2. server-side search over saved modules
3. semantic search over approved knowledge and source excerpts
4. graph-aware search once Marketing Knowledge Graph exists

Search should distinguish between approved knowledge and unreviewed source material.

## Future Knowledge Graph Integration

Knowledge Modules should not be the Knowledge Graph themselves. They should be one source that can publish reviewed knowledge into a graph model.

Recommended graph projection concepts:

```ts
type KnowledgeGraphProjection = {
  moduleId: string;
  publishedAt?: string;
  nodes: KnowledgeGraphNodeRef[];
  edges: KnowledgeGraphEdgeRef[];
  status: "not_published" | "draft" | "published" | "stale";

```

## Migration Strategy

### Phase 0 — Documentation and agreement

This audit is Phase 0. It defines the target architecture and avoids runtime changes.

### Phase 1 — Module registry scaffold, no persistence migration

Create a pure client-side registry file or section that defines known module types and their labels/sections/capabilities. Use it to replace scattered hardcoded title-to-section maps where safe.

Constraints:

- no storage change
- no API change
- no UI redesign
- custom tiles remain source of truth

### Phase 2 — Stable module identity for custom tiles

Add backward-compatible IDs to newly created custom tiles only after an audit and migration plan.

Constraints:

- preserve existing index-based tiles during hydration
- do not delete old user content
- ensure editor selection can resolve either id or legacy index during transition

### Phase 3 — Typed module metadata, still inside Brand Core state

Introduce optional `type` and `metadata` fields for canonical modules only.

Constraints:

- existing custom tile shape remains readable
- no server/API dependency
- no module-specific runtime features yet

### Phase 4 — Module renderer/editor abstraction

Split rendering from Brand Core monolith:

- module registry
- module card renderer
- module editor renderer
- shared action renderer

Constraints:

- preserve existing DOM IDs and event delegation until replaced safely
- migrate one module type at a time

### Phase 5 — Attachments and source material audit

Before uploads, complete a dedicated architecture audit covering:

- storage provider
- security
- file size limits
- accepted file types
- parsing pipeline
- retention/deletion
- privacy
- source provenance

### Phase 6 — AI module actions audit and implementation

Before AI actions, complete a dedicated prompt/runtime audit covering:

- action registry
- context boundaries
- output review state
- provenance/citations
- retry/failure handling
- cost/rate limits

### Phase 7 — Knowledge Graph projection

After typed modules and review state exist, implement a graph projection layer for approved knowledge only.

## Risks

### Architecture drift

If specialized modules are implemented directly as one-off custom tile branches, the system will accumulate inconsistent editors, persistence shapes, and action logic.

Mitigation:

- introduce registry and module lifecycle before specialized modules

### Premature schema migration

Adding module IDs, types, attachments, or history too early could break existing Brand Core snapshots.

Mitigation:

- use additive optional fields
- support legacy custom tile shape
- migrate one capability at a time

### AI trust risk

AI-generated knowledge could be mistaken for approved Brand truth.

Mitigation:

- require review state
- separate source, draft, and approved knowledge
- preserve provenance

### Upload/security risk

Uploads introduce storage, privacy, file-type, and parsing risks.

Mitigation:

- dedicated upload audit before implementation
- module-scoped attachment metadata
- explicit parse/review lifecycle

### Knowledge Graph complexity

Publishing too early could make low-confidence draft content power campaigns.

Mitigation:

- graph projection only from reviewed/approved module knowledge
