# BW-36.20 — Approved Brand Learnings in AI Brain Advice

Status: architecture audit for review; no implementation authorized by this document.

Repository: `Funklix/Funklix`. Audited latest merged `main` at **`6c2712f4f9ca39a5dbbbf0060beb51ce6747bfd4`** (merge of PR #775), verified through GitHub during this audit. Date: 2026-10-15. All source links below are pinned to that commit. Findings describe repository behavior, not a production deployment or database inspection.

## Recommendation and release blocker

Integrate only the existing `/api/ai-brain/advice` consumer. Retrieve currently approved statements on the server from the persisted Board's Brand, independently authorize Brand Learning access, select relevant whole statements deterministically within the provider's actual token headroom, and supply a separately labelled supplementary data block in the existing single provider call. Keep the request body and ordinary answer contract compatible. No new tables, embeddings, background jobs, generation calls, approvals, Profile writes, or campaign writes are needed.

**First fix the Advice Board authorization projection.** The current route passes `getBoardAccess` a column list that omits both ownership columns. The helper interprets absent ownership as an unowned Board and grants a signed-in user edit access before checking membership. Adding Learnings without addressing this defect is not safe. The correction is a prerequisite proposed here, not a code change in this PR. Broader changes to all Board access consumers require a separate review.

Decisions in this document are recommendations awaiting approval. The audit itself changes documentation only.

## 2. Governed Learning storage, lifecycle, APIs and provenance

The implementation authority is [`api/_brand-learnings.js`](https://github.com/Funklix/Funklix/blob/6c2712f4f9ca39a5dbbbf0060beb51ce6747bfd4/api/_brand-learnings.js), not browser catalog state or generated Advisor output.

- `brand_learnings`: UUID identity and required Brand FK; status `proposed`, `approved`, `rejected`, `archived`; normalized statement (1–2,000 Unicode code points), normalized SHA-256 comparison key, optional evidence (up to 4,000), source type `manual`, `campaign_observation`, `ai_suggestion`, proposer/reviewer identity FKs, review time, same-Brand predecessor, BIGINT revision and timestamps. Revisions cross the Learning API as decimal strings.
- `brand_learning_events`: append-only transition history with bounded allowlisted snapshots, actor identity, status transition, Learning revision/time. Events are history, not current approval authority. No individual delete/truncate while the Brand exists; authorized Brand deletion cascades both tables.
- New statements are proposed. Editing a proposal increments its revision. Editing an approved statement creates a proposed successor; the old statement remains approved until human approval of the successor atomically archives the predecessor. Rejection does not approve anything. Archiving approved knowledge removes it from eligibility immediately. Approval does not change `brands.brand_core` or its revision.
- `authorize(client, sessionUser, brandId, write)` (line 123) validates a single active application identity derived from verified session email, checks owner/current Brand member role, and locks Brand, identity and membership in a transaction. Read admits Brand viewers; write requires canonical edit capability. Workspace membership or Board membership alone does not grant Learning access. No runtime DDL in this helper.
- [`api/brands/[id]/learnings.js`](https://github.com/Funklix/Funklix/blob/6c2712f4f9ca39a5dbbbf0060beb51ce6747bfd4/api/brands/%5Bid%5D/learnings.js) provides GET/POST/PATCH with `brand_learnings_v1`, no-store, bounded input/error handling. `operate` owns the transaction, mutations and library readback. `readLibrary` uses 50-row display pages (`LIMIT 51`), counts, source validation and up to ten history events per item. That is a UI contract, not an AI retrieval limit. Do not call this API internally or reuse `operate` just to populate Advice.

Schema evidence: [initial migration](https://github.com/Funklix/Funklix/blob/6c2712f4f9ca39a5dbbbf0060beb51ce6747bfd4/migrations/20261011_bw36_17_governed_brand_learnings.sql), [R1 provenance repair](https://github.com/Funklix/Funklix/blob/6c2712f4f9ca39a5dbbbf0060beb51ce6747bfd4/migrations/20261011_bw36_17r1_learning_provenance_schema.sql), [R2 recovery](https://github.com/Funklix/Funklix/blob/6c2712f4f9ca39a5dbbbf0060beb51ce6747bfd4/migrations/20261012_bw36_17r2_learning_provenance_recovery.sql). The initial Board FK with `ON DELETE SET NULL` conflicted with immutable provenance. The repaired design keeps `source_board_id` as an immutable soft UUID with **no Board FK**, and optional immutable Board-name/node-title/node-type snapshots bounded to 200/300/100 characters. Do not infer final behavior from the initial migration alone. RLS is enabled with browser grants revoked and no browser policies; privileged pg access still requires server ACL.

`sourceRequest`, `validateSource`, `previewSource`, `sourceContext` derive source labels from authorized persisted Board/node data, verify same Brand/Workspace, Board read access and freshness, and fail unavailable sources safely. `sourceContext` can return `available:false` when a Board/node disappeared, moved or became inaccessible. It is internal, not exported. Display snapshots are historical labels, not current source authorization or independently verified evidence. Initial integration should not dereference source Boards or include these labels in the provider payload.

[`api/_learning-advisor.js`](https://github.com/Funklix/Funklix/blob/6c2712f4f9ca39a5dbbbf0060beb51ce6747bfd4/api/_learning-advisor.js) is a separate consumer: `loadScope` uses Learning authorization plus Workspace/saved Board scope and reads both approved and proposed Learnings for analysis/deduplication. It fingerprints input, revalidates after inference and uses governed proposal adoption. Its `analyze`, `prepare`, `adopt` and `adoptSelected` must not be invoked or changed by this integration. They can perform multiple paid calls and intentionally serve different permissions and lifecycle semantics.

## 3. Active Brand, Board, Profile, DNA and strategy context

For Advice, the active Brand must mean **the currently persisted Brand association of the authorized Board**. A selected Brand with no Board does not currently enable Advice. [`app.js` `selectedBrandPreferenceId` (line 3119), `renderBoardBrandAssociation` (line 4632), association save (around 4776), and `canvasLearningContext` (line 14073)](https://github.com/Funklix/Funklix/blob/6c2712f4f9ca39a5dbbbf0060beb51ce6747bfd4/app.js#L3119), [`brand-sidebar.js` `project`](https://github.com/Funklix/Funklix/blob/6c2712f4f9ca39a5dbbbf0060beb51ce6747bfd4/brand-sidebar.js), and [`workspace-catalog.js` `deriveActiveWorkspaceId`](https://github.com/Funklix/Funklix/blob/6c2712f4f9ca39a5dbbbf0060beb51ce6747bfd4/workspace-catalog.js) distinguish selected/viewed Brand, Board association and Workspace. These client values support presentation; none should authorize provider knowledge.

| Knowledge | Actual Advice contribution | Consequence |
| --- | --- | --- |
| Canonical Brand Profile | Raw `brands.brand_core`, optional after independent Brand read check, with revision/update time | Current reusable Profile; no automatic sync or profile rewrite |
| Campaign snapshot | Raw `boards.brand_core_snapshot`, source revision/time | Campaign-specific saved context; may intentionally lag or differ from canonical Profile |
| Brand DNA | Nested data in these raw Core objects, if present | Advice does not check `brandDNA.userApproved` or apply a dedicated DNA projection; do not describe all DNA as human-approved |
| Market Research / Business Plan | Raw nested `customTiles` can reach Advice with either Core object | Advice currently does not filter draft modules or separate accepted facts from assumptions |
| Other/private document modules | Raw nested Core properties can reach Advice | Existing privacy/context-minimization risk; no new document retrieval should be added |
| Canvas and diagnostics | Client working projection plus server deterministic analysis | Working material and qualitative structural findings; not approved Brand truth or measured performance |

[`api/_brand-brain-context.js`](https://github.com/Funklix/Funklix/blob/6c2712f4f9ca39a5dbbbf0060beb51ce6747bfd4/api/_brand-brain-context.js) exports `normalizeBrandBrainData`, `buildBrandBrainContext`, `buildArchetypeGuidance` and `projectAcceptedStrategyModule`. The accepted strategy projector validates stable module IDs, accepted lifecycle/revision/time, bounds narrative/facts and separates assumptions. The normalizer omits `pitch_deck` and `whitepaper` from custom context. **Advice imports none of these helpers.** Other AI routes and the Learning Advisor do use them. Adding Learnings to `buildBrandBrainContext` would therefore miss Advice and expand unrelated consumers. Its existing archetype guidance orders Positioning > ICP > Value Proposition > Messaging Pillars > Archetype > Tone, but Advice does not currently apply that generated text.

Use the existing pure accepted-module projector if later adding an Advice-specific allowlisted Core projection; do not silently replace raw Core context with the shared normalizer as part of Learning retrieval. That would alter existing Advice evidence coverage and needs its own compatibility/privacy decision. Minimum Learning integration must at least label nested draft/generated material and state that it does not acquire Learning approval merely by appearing in the same payload.

## 4. Exact missing capabilities and proposed retrieval/authorization design

Missing today: a server-only approved-Learning reader; independent Learning identity/ACL validation in Advice; relevance ranking; a total provider input budget; an explicit Learning trust/precedence policy; provider-boundary and return-boundary revalidation; coverage metadata; optional validated source attribution. Existing browser invalidation does not include live Learning revisions or canonical Profile revision and cannot substitute for server checks.

Recommended flow, with no new request fields:

1. Preserve current body/session/Canvas/conversation validation and no-provider clarification behavior. Correct Advice's Board access column list to include **`owner_email` and `owner_id`** wherever using `getBoardAccess`. Never return these ownership fields in provider context. Test real membership resolution.
2. Use a short transaction on the existing pg pool. Resolve/lock the Board row with required ownership, Brand association, snapshot and update time; run `getBoardAccess` on that client. Keep Board edit requirement. Derive `brandId` solely from that locked Board. Resolve canonical access on the same client with `skipEnsure:true` to avoid adding runtime schema work. Existing `getBrandAccess` defaults to `ensureBrandsTable` and relationship reconciliation; do not invoke those through the new reader.
3. When Brand read is available, call the existing Learning `authorize(client,user,brandId,false)`. This adds active application identity and current Brand membership validation without requiring edit permission. A Board editor who is also a Brand viewer can consume Learnings; a Brand viewer without Board edit access still cannot ask Advice. Do not impose the Advisor's write role or Workspace-generation contract on Advice.
4. Query only `brand_learnings WHERE brand_id=$1 AND status='approved'`, parameterized. Project only ID, revision as string, statement, approval time and minimal ranking fields (`source_board_id`/`source_node_id`, retained server-side). Never send actor identities/emails, events, proposed successors, raw source Canvas, receipts or source labels. Evidence summary is omitted initially: it increases context and may contain source-specific or injected material beyond the approved statement.
5. Rank all eligible records via the deterministic selection below, collect selected `(id,revision)` and a fingerprint of the included Board/snapshot/canonical context. Complete database work and release locks before inference. For a large library, bounded keyset batches under a consistent read snapshot avoid a UI page limit and unbounded memory. A scan/runtime failure must not be presented as a complete empty library.
6. Immediately before sending provider input, revalidate Board edit access, persisted Brand association, Learning identity/read authorization, included Profile/snapshot versions and selected records' current approved status/revisions in a short transaction. If changed, return a retryable context-changed response with zero provider calls; do not silently reuse stale context. Do not hold database locks over tokenization or the provider call.
7. Make the existing one provider call. Before returning its answer, repeat those authorization and selected-version checks. Suppress the **entire answer** on revocation, archive/supersession, Brand reassociation/deletion or included Core change; removing citations cannot remove facts already influenced by revoked knowledge. Return a bounded retryable failure, without Learning details. Do not automatically make a second paid request.

Lock ordering must be reviewed against Board writes: use Board-first ordering with nonblocking/short bounded lock acquisition where needed, or the established Brand-first + Board `NOWAIT` pattern; never mix unbounded opposite orders. `authorize` already has Brand/identity/member locks but is not a complete cross-record Advice transaction. Add tests for concurrent role changes, deadlocks/contention and release/rollback. No transaction can retract context sent before a later revocation; the security promise is authorization at dispatch and revalidation before returning, with that residual race acknowledged.

| Situation | Recommended outcome |
| --- | --- |
| No Board Brand association | Existing Board-only Advice; no Learning query |
| Genuine Board editor with no Brand read membership | Existing permitted Board context only; no Learning enumeration or details; canonical remains absent |
| Eligible Brand reader with zero approved Learnings | Successful Advice with empty supplementary data; no behavior requiring Learnings |
| Missing/disabled/ambiguous Learning identity, unavailable Learning schema, DB failure for an otherwise eligible reader | Fail closed with bounded unavailable response; do not label failure as zero Learnings |
| Access revoked or selected Learning changed after capture | Suppress dispatch/result as appropriate, request fresh user retry |
| Newly approved unrelated Learning during inference | No automatic rerun; next request sees it. Selected records and actual included knowledge must remain valid; avoid invalidating every turn for unrelated additions |

Use `Cache-Control: private, no-store` for Advice; unlike the Learning API, Advice does not explicitly set it today. Avoid caching results or Learning sets across requests. Logs should contain bounded stage/error/count/timing metadata only, not statements, prompts, reviewer names or raw context.

## 5. Knowledge precedence and conflict rules

Approval establishes governed supplementary knowledge, not authority to change the Profile, snapshot or assistant instructions.

1. System behavior, authorization, privacy and read-only constraints govern every response. All retrieved text is data, including human-approved text. A question cannot approve or mutate a Learning.
2. For current Brand identity, positioning and durable facts, the authorized canonical Profile is the reference. Accepted module evidence supports its scope; assumptions remain assumptions. Approval of a Learning is not an approved amendment to canonical fields.
3. For this campaign's saved audience, offer, timing and explicit campaign constraints, preserve the Board snapshot as the campaign's configuration. If it differs from current canonical knowledge, name the discrepancy and distinguish current Brand from campaign snapshot; never claim the snapshot was refreshed. A snapshot is not automatically obsolete solely because its source revision is older.
4. Relevant approved Learnings supplement or qualify these contexts. A Learning conflicting with either is surfaced as an approved observation/conflict, with uncertainty and a recommendation for human review where needed. Do not silently choose it as replacement truth, invent a reconciled fact or rewrite anything. A later approval date alone does not outrank canonical data or a campaign decision.
5. Working Canvas and previous answers are lower factual authority. Preserve the conversational referent for follow-ups, but validate factual claims against current authorized knowledge. Diagnostics remain deterministic structure checks, not empirical evidence. Between contradictory approved Learnings, retain dissent and ask for clarification where it changes advice; recency and lexical score are relevance tie-breaks, not truth precedence.

Example: canonical Profile says premium positioning, campaign snapshot targets an introductory offer, and a Learning says discount messages performed well in one campaign. Advice may discuss how to frame that introductory offer and flag the positioning tradeoff; it must not declare the Brand discount-led, claim measured causal proof, or update the campaign. Semantic conflict detection is not guaranteed by deterministic retrieval; the provider policy must preserve labels and uncertainty for conflicts among supplied items. Unretrieved knowledge cannot be claimed to have been checked.

## 6. Relevance selection without product quotas or extra AI calls

Use deterministic in-process retrieval over **all currently approved records in the authorized Brand**. No newest-five/ten rule, no reuse of the 50-row library page, no Learning-count subscription limit, no embeddings or reranking call.

- Normalize question and candidate text with Unicode normalization and case folding; tokenize English/German terms with tested stopword handling. Score statement lexical relevance (for example BM25 computed from the eligible set), with question matches primary and selected node title/type/audience/channel and connected working context as secondary signals. Whole-Canvas generic terms must not overwhelm the question. Provenance match to current Board/node is a secondary relevance boost, never eligibility or truth authority. A soft source ID is only a ranking hint.
- For a follow-up, use the bounded most recent relevant assistant text as a low-trust lexical hint so “the second idea” can find related statements; it cannot authorize an ID or override the question. Deterministic lexical retrieval cannot guarantee semantic or bilingual synonym recall. Record this limitation; use a small explicit domain synonym map only if reviewed, not model-generated query expansion.
- Rank by declared relevance components, then stable deterministic ties (approval time and ID); deduplicate normalized statements. No positive match means select none and report that outcome, not that the Brand has no knowledge. For an explicitly broad “use all Brand Learnings” question, stable ordering may include all that fit, with partial coverage declared.
- Account for the **entire serialized provider input**: policies, both Core objects, working Canvas, diagnostics, history, language, question, Learning envelope, protocol margin and reserved output. A 350 KB HTTP bound is not a token budget. Use existing `js-tiktoken` dependency; known model context/encoding can follow the pattern in Advisor `modelConstraints`/`fits` (lines 342–371), but those exported helpers are Advisor-specific, include its schema and 8,192-output reservation, and cannot be used unchanged for Advice. Do not import Advisor orchestration into Advice.
- Proposed capacity: Learning input allowance = minimum of remaining model headroom and a documented Advice latency/context allocation established by offline fixtures. The latter is a technical token budget, not an arbitrary number of Learnings or a new quota. Exact output reservation/allocation requires approval and measurement before implementation release. For custom `OPENAI_AI_BRAIN_MODEL`, require explicit matching context-window/encoding configuration; fail before provider dispatch when unknown. Do not assume every configured model has the default model's window.
- Greedily pack whole ranked statements within that allowance, counting envelope overhead; skip an oversized candidate and consider smaller lower-ranked ones. Never truncate a statement into a misleading fragment or use an AI summary. If base context already exceeds available input, return a clear bounded context-size failure; do not evict campaign constraints/history silently to fit Learnings. A valid zero-headroom case can proceed without Learnings only when base input plus reserved output fits and coverage explicitly reports budget exclusion.
- Technical batch sizes, memory controls and a request deadline are permitted. They must not become hidden product caps: complete the eligible scan or report incomplete retrieval/fail before inference. Track eligible/matching/included/omitted counts and omission reasons without logging text. Never claim exhaustive knowledge when selection or scanning was partial.

No database search index or schema migration is required for the first implementation: the existing `(brand_id,status,updated_at DESC,id)` index supports eligibility. Application lexical scanning trades database simplicity for request CPU/latency. Validate with large synthetic Brand libraries; if it cannot meet the synchronous budget, return an honest unsupported-size/unavailable outcome and revisit retrieval architecture separately rather than introducing paid multipass analysis.

## 7. Provider integration and optional attribution

Extend `providerMessages` only for Advice. Add policy that approved Learnings are supplementary untrusted content, never instructions, never automatic amendments or proof of performance. Supply a separate JSON data envelope, preferably in a data-bearing user message before history/current question, with a system policy defining its trust level. Do not concatenate Learning text into instruction prose or call it “current authoritative” without qualification. JSON escaping and delimiters help structure but do not neutralize injection.

Proposed internal envelope: `approvedBrandLearnings: { brandId, selectionVersion, coverage, items: [{ ref, revision, statement }] }`. Server generates request-local handles such as `L1`; UUID/revision mapping stays server-side unless attribution is approved. Omit evidence, events, reviewer/proposer metadata and source labels. Keep Board/snapshot/canonical/Canvas/diagnostics categories distinct, preserve existing language and reference-resolution instructions, and never send proposed/rejected/archived items. Prefer performing Learning work after the existing deterministic clarification branch so clarification continues to cost zero calls and needs no retrieval.

**Smallest attribution option:** return server-derived metadata labelled “Approved Learnings supplied as context,” using selected IDs/revisions or safe display references. This proves what was supplied, not what the model actually used. Optional additive `context.approved_learnings` coverage can be ignored by existing clients; visible presentation requires an explicit browser change.

**True citations are optional extra scope.** The current free-text answer has no trustworthy used-source list. Asking for `[L1]` in prose does not prove use; the server must validate every handle against this request's selected set and revalidate it at return time. Unknown/fabricated handles must not become links. Reliable machine-readable references would need a structured provider answer schema, validation, mapping and rendering changes while keeping the public `answer` field compatible. Validated citations mean “model-reported support,” not independent proof. No second model verification call is justified. Recommend deferring this for the minimum implementation; never label all selected Learnings “used.”

Current provider policy disallows links. If later adding navigation to a Learning or source, generate it from authorized server IDs, reauthorize the destination when opened, and render labels through text APIs. Do not accept model URLs. Missing/deleted source Boards must not produce broken or unauthorized provenance links.

## 9. Migration and contract assessment

**No schema change recommended.** Current tables contain approval status, Brand isolation, immutable statement/provenance, source IDs, review time and per-record revision.
