# Audits

Audits document what was inspected before implementation. Major features should have an audit before code changes begin so risks, dependencies, and blast radius are understood.

## Audit Format

Use the following structure for future audit documents:

- **Date** — when the audit was performed.
- **Topic** — the feature, issue, system, or decision area being audited.
- **Current behavior** — what the product or code currently does.
- **Goal** — what the proposed work is trying to achieve.
- **Files/functions inspected** — exact files, modules, functions, or docs reviewed.
- **Risks** — known risks, unknowns, regressions, or product concerns.
- **Blast radius** — areas likely to be affected by the change.
- **Recommendation** — recommended path forward.
- **Decision** — accepted direction after review.
- **Follow-up** — remaining questions, cleanup, tests, or docs work.
