# BW-34.1.4 — Social publishing end-to-end audit

**Audit date:** 2026-09-14 (UTC)  
**Scope:** current merged `work` tree at `5fc22f6`; read-only static analysis and Git-history review.  
**Classification vocabulary:** **Proven** means directly established by current code/history; **strong inference** joins directly established code paths but lacks the affected production node; **unknown** identifies evidence the repository and supplied production observations do not contain. No credentials, provider API, database write, publication, migration, configuration change, production-code change, or newly invented test was used.

## 1. Executive conclusion

The workflow does not have one canonical publication state. It has at least four independently derived concepts:

1. editorial completeness (`calculateReadiness`), which accepts `social.caption || content`, ignores media, and is explicitly not publish capability;
2. approval material (`approval-material-contract.js`), which fingerprints caption, images, variants and other fields, but excludes links, preview, schedules, approval metadata and provider delivery state;
3. Facebook payload support (`validateFacebookContent` in the browser and `evaluate`/`normalizeMessage`/`normalizeLink` on the server), which requires `social.caption`, rejects every non-empty `images` array, and interprets only a whole-string URL in `social.preview` as a link; and
4. primary-action policy (`primaryDecision`), which layers editorial status, transient browser maps, platform strings, the Facebook connection projection and payload validation.

That separation makes the reported Facebook card internally consistent in code, although misleading to a user: **“Ready” only means title + platform + usable caption/content + CTA heuristic; “Unsupported Facebook content” means one of six payload validation failures.** The connected Page is not implicated after the supplied production evidence and the unified selector: destination selection is evaluated before payload support and the observed label is emitted only from the selector’s selected Page.

### Root-cause verdict

**Proven:** the exact label is emitted only when `primaryDecision` receives `facebook_payload_unsupported`, which is returned only when `validateFacebookContent(node).ok === false`. The six browser causes are: missing/non-string/invalid-Unicode `social.caption`; empty normalized caption; more than 63,206 Unicode code points; any non-empty `node.images` array; multiple distinct link candidates; or an invalid candidate URL. Ordinary URLs embedded in prose are not candidates. `title`, `content`, metadata, attachments outside `images`, and an empty `images` array do not independently trigger the label.

**Proven compatibility defect:** a Social Media Posting generated by **Generate next step** from a parent with images inherits every parent image (`generateNextStepFromNode` passes `parentId`; `createNode` copies `parent.images`). Its visible caption remains ordinary text and readiness ignores images, while both Facebook validators reject `images.length > 0`. This is a deterministic current-code route to precisely the observed contradiction. Full progressive campaign generation passes `parentId: null`, so that separate generator starts with `images: []`.

**Unknown for the particular production card:** the repository contains neither that node’s sanitized persisted JSON nor the validation code selected at runtime. Therefore it would be false to claim statically that its exact failing field is definitely `images`. The smallest safe proof is a **read-only, redacted projection of that one board/node containing only** `id`, `type`, `status`, `channel`, `social` field names/types and bounded values (`platform`, caption presence/code-point count, `link`, `url`, `preview`), `images.length`, and the result `{code}` of the already-deployed pure `validateFacebookContent`; no token, destination external ID, user data, provider call, or publication is needed. The current UI throws the specific code away, so the production screenshot cannot discriminate the six causes.

### Other conclusions

* The structured approval 4xx is server-authoritative but the client collapses every non-authentication rejection into `approval_rejected`; its copied diagnostic omits the server’s safe `failure_category` and `rejected_field`. The exact branch for the observed request is therefore **unknown from the supplied generic classification**, while all possible current 4xx branches are enumerated in section 3.
* LinkedIn’s indefinite “Saving and verifying approval…” is an independent browser lifecycle defect: an already-approved node loaded from storage has no `approvalPersistenceByNode = "saved"` entry, and LinkedIn’s action requires exactly `"saved"`. Facebook’s current branch does not impose that transient-map requirement.
* Instagram and every approved non-Facebook/non-LinkedIn Social Media Posting fall through to `plan`, so “Schedule” is an **internal board-planning write**, not Instagram/provider scheduling. The menu also offers this internal action beside provider actions.
* A successful Facebook publish is durable in publishing tables, but the node itself is not finalized. The browser’s in-memory `finalizedFacebookByNode` supplies the immediate card state; a reload loses it and the client cannot know the durable external post until server preflight rejects it as `already_published`.

## 2. Exact proven root cause of “Unsupported Facebook content”

### Label path

1. `projectAsset` chooses platform from `social.platform || channel` and preview from `primaryContent`, which itself chooses `social.caption || content` for Social Media Posting.
2. `primaryDecision` enters the Facebook branch only for exact role `Social Media Posting`, lower-cased platform `facebook`, normalized `Approved`, and a locally current non-v1 approval.
3. `facebookAction` calls `selectFacebookPublishingReadiness` with the current connection snapshot and the live `getNode` result (not the projected card).
4. The selector orders blockers: unresolved snapshot → disconnected → invalid selected destination → no selected destination → not approved → stale approval → invalid payload → already published → ready.
5. When validation is invalid it returns `reason: "facebook_payload_unsupported"`.
6. `actions` maps exactly that reason to `t.unsupportedFacebook`, displayed as **“Unsupported Facebook content”**, and disables the button.

Thus the observed Page label and unsupported label can coexist without stale selector inputs. The Page label and action both use the same selector. The contradiction is between the selector and the independent readiness badge.

### Complete browser validation causes

| Code retained internally | Exact condition | Can look like ordinary visible text? | UI explanation today |
|---|---|---:|---|
| `facebook_content_invalid` | `social.caption` is not a string, contains NUL, or contains an unpaired UTF-16 surrogate | Yes: card preview can fall back to `content` | Generic unsupported label; code not shown |
| `facebook_content_empty` | normalized `social.caption` is empty | Yes: card/readiness can fall back to `content` | Generic |
| `facebook_content_too_long` | normalized caption exceeds 63,206 Unicode code points | Yes | Generic |
| `facebook_media_unsupported` | `Array.isArray(images) && images.length > 0` | **Yes; proven generator compatibility route** | Generic |
| `facebook_link_ambiguous` | two or more distinct non-empty candidates among `social.link`, `social.url`, and URL-shaped whole `social.preview` | Yes | Generic |
| `facebook_link_invalid` | chosen candidate is malformed or not HTTPS, or contains credentials, explicit port, or fragment | Yes | Generic |

An empty array/object is not treated as media unless `images` is an array with positive length. Generated `metadata`, `hashtags`, `variants`, `imagePrompt`, `favoriteImageId`, and `landingPage` are not mistaken for media. A URL **inside normal caption copy** is never parsed by this validator. A preview is a link only when the entire trimmed preview begins with a URI scheme; prose containing a URL is not.

### Actual generated value paths

* `createNode` defaults every node to `social.platform = "Instagram"`, empty caption/preview, and `images: [...images]`.
* The current campaign API requires full post text in `social.caption`, a short summary in `content`, and metadata channel. `applyGeneratedCampaignNodePayload` selects `payload.social.platform || node.channel || "LinkedIn"`, copies the payload caption (falling back to content/title), writes the same caption to `node.content`, writes the description to `social.preview`, and synchronizes `channel` to platform. Progressive campaign creation uses `parentId: null`, so no parent image inheritance occurs.
* The older/general next-step path creates the child with `parentId: sourceNode.id`; `createNode` copies the parent’s images into a Social Media Posting. `applyGeneratedNextStepContent` then sets caption from generated content but does not remove inherited images. This path yields readable copy plus `facebook_media_unsupported` after the platform is Facebook.
* Inspector edits synchronize the platform select to both `social.platform` and `channel`; caption and generic content remain independently editable. Canvas inline editing changes `social.caption`. Persistence sanitizes image objects but does not remove supported-looking images from a social node.

### Direct answers

**Why does a visible, ordinary text Facebook post become unsupported?** Because visible copy and review readiness permit fallback to `content`, while Facebook requires `social.caption` and additionally rejects any `images`. For next-step-generated children of an imaged parent, the precise deterministic cause is inherited `images`; for the particular production node, the current generic UI does not expose whether that or one of the other five codes fired.

**Is displayed Facebook text exactly what the server would send?** If `social.caption` is a valid non-empty string, both card and server use it; browser/server normalize BOM, CRLF and outer whitespace before sending, so the visual source is semantically the same but not byte-for-byte identical. If caption is empty/non-string and `content` is visible through the UI fallback, **no**: the server will reject rather than send `content`. `title` is never prepended. Hashtags are not appended. The Inspector’s preview/link field is not appended to message; it may become the separate `link` parameter.

## 3. Exact proven approval failure branches

### Endpoint command boundary (`api/content-review/approve.js`)

| HTTP | Response `status` | Safe `failure_category` / stable service code | Preconditions | Retry without edit? |
|---:|---|---|---|---|
| 405 | `request_invalid` | `method_not_allowed` | Method is not POST | No; caller defect |
| 401 | `authentication_required` | `authentication_required` | No session identity | Only after session recovery |
| 400 | `request_invalid` | `invalid_approval_command` | Body not plain object; extra key; invalid board UUID/node/client request ID; expected status not exactly `In Review`; or malformed optional v2 fingerprint | No; request must change |
| 404 | `approval_rejected` | `board_not_found` | access resolver returns no board | Only if board/access visibility changes |
| 403 | `approval_rejected` | `board_edit_access_required` | authoritative access lacks edit | Only if access changes |
| 404 | `approval_rejected` | `node_missing` | locked authoritative board has no node ID | No for deleted node |
| 409 | `approval_rejected` | `approval_status_invalid` | stored node status is not exact `In Review` | A reload may reveal it; otherwise transition must change |
| 422 | `approval_rejected` | `readiness_incomplete` | authoritative caption or platform is empty | Requires edit |
| 422 | `approval_rejected` | `warning_acknowledgement_required` | no CTA/link heuristic and command did not acknowledge warning | Yes, with acknowledgement; UI confirmation normally supplies it |
| 409 | `approval_rejected` | `material_expectation_changed` | supplied fingerprint differs from locked node fingerprint | Only after authoritative reload/review; blind retry repeats |
| 500 | `response_construction_failed` | `response_construction_failed` | authoritative envelope safety failure | Operational repair |
| 503 | `storage_unavailable` | `approval_write_failed` | thrown database/storage path | Yes when service recovers |

On every service rejection the server rolls back and leaves the authoritative node `In Review`. On success it locks the board row, changes status to `Approved`, stores the v2 fingerprint and bounded approval metadata, optionally appends board activity, updates `canvas_json`, commits, and returns the new board revision.

### Client handling and loss of reason

`readAuthoritativeJson` correctly recognizes the authoritative envelope even on non-2xx responses and categorizes it as `structured_failure`. `requestAuthoritativeContentApproval`, however, special-cases only `status === authentication_required`; every other structured rejection becomes client category `approval_rejected`. It records the server request ID but does **not** copy `result.failure_category`, `result.rejected_field`, `retryable`, or the HTTP status itself into the rendered/copyable failure reason. The card shows only “Approval could not be completed. The content remains In review.”

For failures before a successful approval response, no authoritative reload is attempted. For a successful response, the client GETs the board with `cache: no-store` and demands matching node fingerprint, exact status, exact board `updated_at`, and recomputed material. Reload/network/board-generation failure becomes `authoritative_reload_failed`; missing or mismatching node becomes `node_reconciliation_failed`.

Pending release is bounded in two layers: `openDialog` deletes `approvalPendingByNode` in `finally`; `requestAuthoritativeContentApproval` changes the persistence map from `saving`/`verifying` to `error` in `finally` unless it reached `saved`. Therefore a normally settled request does not remain pending. A fetch with no timeout can remain unresolved indefinitely, however, so neither `finally` executes. The diagnostic’s `pending_state_release_category: "released"` is initialized before release and is therefore an assertion, not observed lifecycle evidence.

### Which branch produced the observed Facebook 4xx?

**Unknown from the supplied diagnostic.** Its tuple (`approval_failure`, `approval_rejected`, `structured_failure`, `4xx`) matches every endpoint service rejection in the 403/404/409/422 rows and also a 400 command rejection after parsing; the client discarded the discriminating safe category. The smallest safe evidence is the existing approval response body or Vercel log for its `server_request_id`, specifically only HTTP status, `status`, `failure_category`, `rejected_field`, and `retryable`. No OAuth or provider interaction is relevant.

## 4. Explanation of the LinkedIn pending-state symptom

**Proven and independent of the Facebook rejection.** `approvalPersistenceByNode` is an in-memory `Map`, initially empty. It is populated as `saving`, `verifying`, then `saved` only during a successful approval in the same page lifetime. Hydration/reload does not reconstruct `saved` from authoritative node status/fingerprint. Yet `primaryDecision` says every approved/current LinkedIn post is `saving` unless `approvalPersistence(id) === "saved"`. Consequently an approved LinkedIn node loaded on a new page, loaded before the map existed, or approved in another client can display “Saving and verifying approval…” forever even though no request is running.

Facebook used the same gate before BW-34.1.3 but its current branch publishes directly from the selector’s approval currency. The Facebook 4xx path sets the map to `error` and exposes a retry failure card rather than creating this LinkedIn hydration condition. They share UI wording/maps but are different causes. A genuinely never-settling approval fetch can also hold either platform pending because no timeout exists; that is a second, network-lifecycle possibility and needs browser network timing to distinguish.

### Canonical-material mismatch with publication

Approval is over-inclusive for Facebook (`content`, title, hashtags, images, variants, CTA, audience, tone can stale approval although several are not sent) and under-inclusive (`social.link`, `social.url`, `social.preview` can change payload/support without changing the fingerprint). The mutation helper uses approval serialization, so an approved node’s link can change without returning to Draft. This proves approval and publishing do not share one canonical material contract.

## 9. State-machine and refresh lifecycle

### Node/editorial lifecycle

```text
Draft --submit--> In Review --approve (server transaction)--> Approved
Needs Changes --resubmit--> In Review
In Review --request changes + note--> Needs Changes
Approved --reopen--> Draft (fingerprint removed)
material edit detected by shared serializer: Approved/fingerprinted --> Draft
internal planning: adds/removes planningSchedule; does not change status
provider publication: writes social tables; does not change node status
```

Browser transition preparation snapshots identity/status/readiness/fingerprint. `applyContentWorkspaceTransition` resolves the live node, account, board and access, rechecks status/material/readiness and warning/note requirements. Non-approval transitions mutate local state and mark it unsaved. Approval computes a browser v2 hash from the persistence-sanitized node, POSTs only command metadata, and relies on the server’s locked copy.

### Approval refresh lifecycle

```text
confirm → approvalPending add + persistence=saving
→ browser fingerprint → POST approval
  rejection: no board reload → persistence=error; pending removed; generic failure card
  success: persistence=verifying → no-store board GET
    verified: replace live node with authoritative node → persistence=saved
    mismatch/failure: persistence=error; server may already have committed Approved
finally: render; outer finally removes approvalPending and renders
```

A post-commit reload failure creates a split outcome: server is Approved but local node remains In Review until a later board load. Retrying immediately sends expected `In Review` and can receive `approval_status_invalid`. This explains how retry may not succeed without reload even though the original approval actually committed.

### Publish lifecycle

```text
primary publish → browser fetches current connections → POST provider preflight
→ server reloads board/node/access + connection/credential/destination/jobs
→ approval three-way boundary + eligibility
→ confirmation dialog uses server caption/destination
→ POST publish (confirmed) → idempotent job queued → delivering
→ provider attempt started → adapter request
→ provider accepted → attempt accepted → external post + job delivered transaction
→ immediate result or bounded job polling (8 iterations)
→ in-memory Facebook finalization + render, or durable diagnostic/uncertain stop
```

The publish route never trusts the browser’s caption, Page label, external Page ID, or credential. It uses internal destination ID and authoritative node. Provider-accepted but incompletely persisted outcomes become `provider_accepted_unreconciled`, `reconciliation_required`, or `outcome_unknown`; the UI removes retry for uncertain states and offers bounded diagnostics.

### Final UI lifecycle defect

Successful Facebook publication populates only `finalizedFacebookByNode` in memory and calls `onRefresh`, which is merely a render. No board reload or node field write occurs. A browser reload therefore loses the success banner/`alreadyPublished`; server idempotency remains the final protection. Job polling uses the shared job route backed by the LinkedIn service registry; registry/platform behavior was introduced for both, but the job result service chosen by `route.service()` is `createPublishingService` (LinkedIn). Because the table rows share shape, basic lookup works, but Facebook-specific reconciliation/classification logic is not selected. This is a provider-dispatch overlap requiring explicit verification in repair work.

## 10. Historical-data compatibility findings

1. **Legacy role:** some analytical code maps `Social Media Post` to `Social Media Posting`, but Content Workspace, approval and publishing require the latter exactly. Compatibility is partial.
2. **Platform defaults:** every new node begins with `social.platform: "Instagram"`; the platform fallback therefore masks `channel` until a synchronized writer changes `social.platform`. Historical nodes with `channel: Facebook` and stale truthy `social.platform: Instagram` are treated as Instagram.
3. **Case:** provider selection in cards lower-cases platform, and server lower-cases it; scheduling uses exact case-sensitive membership (`LinkedIn`, `Instagram`, `Facebook`, `X / Twitter`, `TikTok`). Filters are exact-case too.
4. **Generator mismatch:** Facebook was added to UI selectors, but campaign prompt logic still describes Mixed distribution across LinkedIn, X, Instagram and TikTok and has LinkedIn-specific content quality. Facebook may arrive from an explicit channel, yet no Facebook-specific generated media contract prevents unsupported images/links.
5. **Two generation shapes:** campaign API says `content` is a short summary and caption is full copy, but current `applyGeneratedCampaignNodePayload` overwrites `content = caption`. Older next-step generation also maps generated content to caption. Historical nodes can therefore contain summary/content/caption disagreement.
6. **Image inheritance:** parent-generated next steps copy images into social children; Facebook explicitly supports no media. This predates the Facebook surface.
7. **Link compatibility:** `social.link`, `social.url`, and URL-shaped `social.preview` are payload fields but excluded from approval. Preview is also routinely populated with generated description, making it dual-purpose metadata/link storage.
8. **Duplicated implementations:** browser readiness, browser Facebook validation, server Facebook validation, approval-service readiness, Content Workspace readiness, Facebook service readiness, LinkedIn service readiness and scheduling eligibility are separate functions.
9. **Fallback content:** UI readiness/preview uses caption or content; approval and provider use caption without fallback. This is the principal text-representation disagreement.
10. **Truthy structures:** non-empty `images` arrays block even if entries are empty/metadata-only; non-array media/attachments are ignored. Approval’s `approvedObject` discards nested object/array values inside images/variants, while persistence retains a fixed image shape.
11. **Status normalization:** browser maps aliases/case variants; server approval/publish expects exact strings.
12. **Publication compatibility accessors:** browser checks historical `facebookPublication`/`externalPublication`, but current server publication never writes them. These are stale compatibility readers rather than current authority.
13. **History overlap:** BW-34.1.1 introduced browser Facebook validation/action alongside existing LinkedIn logic; BW-34.1.2 made Page selection durable; BW-34.1.3 unified Page label/action around one snapshot but deliberately left server eligibility and content contracts unchanged. It removed the transient `saved` gate for Facebook only, leaving LinkedIn’s pending behavior.

No historical node should be rewritten merely by reading/projecting it. Current code generally honors that for schedules and nodes; a future compatibility repair can normalize at payload projection without migration, subject to approval semantics below.

### Explicit compatibility answers

* **Can an existing approved Facebook node be made publishable without recreating it?** **Yes in principle.** If its only issue is a representation mismatch or unsupported inherited image that is not intended for this text-only publish, a canonical non-mutating publication projection can use/validate the intended existing fields. If persisted material must be edited/removed, current mutation semantics return it to Draft. No recreation is inherently required.
* **Must approval be repeated if only payload normalization changes?** If normalization only makes the server and browser interpret the already-approved, fingerprinted fields identically and does not change the approval-material bytes or outgoing semantic content, **no**. If it changes which field supplies message/link, omits approved images, appends hashtags/title, or otherwise changes sent semantics, approval **must** cover that canonical payload first. Current links are not fingerprinted, so merely retaining current behavior does not make them safely approved.
* **Can the primary action come from one authoritative state machine?** Yes. The current code already demonstrates a pure Facebook selector, but a complete machine must accept authoritative connection/destination/publication capability, canonical material/fingerprint, payload result with exact blocker, platform connector capability, access, and internal-planning capability, then return label/action/explanation from one ordered decision. Server preflight remains final authority.

## 11. Production observability gaps

| Failure stage | Safe diagnostics now | UI sufficient? | Vercel/log sufficiency |
|---|---|---|---|
| Approval command/rejection | authoritative response has request ID, safe category, rejected field, retryable; client diagnostic has request IDs and coarse phases | **No:** safe server reason discarded | Only if request ID and structured body/category are logged externally; repository has no explicit approval structured logger |
| Browser payload rejection | pure validator returns exact code | **No:** six codes collapse to one label and are absent from copy diagnostics | No request occurs, so no server/Vercel evidence |
| Publish preflight | response has `status`, blockers and approval diagnostic/request IDs | Partial: stale approval has copy diagnostics; other status is shown as terse raw text and blocker detail may be lost | Server response is enough if retained; no explicit structured logging found |
| Meta rejection | adapter maps HTTP/code to bounded classification; publish result/job stores safe classification | Partial generic failure + copyable lifecycle IDs | Durable job/attempt safe columns are enough with owner/job ID; raw secret/body should not be needed |
| Persistence failure before delivery | `storage_failed_without_delivery`, sometimes job ID | Partial; generic publication failure but diagnostic can identify no committed delivery | Enough if response/job exists; insert failure without job has only request ID/classification |
| Accepted/ambiguous outcome | job/attempt states, provider reference retention category, external-post state, duplicate prevention | Best-covered: warning, no blind retry, copy diagnostics, polling | Durable rows usually sufficient; Facebook job polling currently uses generic/LinkedIn service dispatch, which can weaken reconciliation interpretation |

The safest minimal evidence for the two unresolved production facts is:

1. unsupported card: bounded node shape + deployed validator code/result described in section 2;
2. approval 4xx: response/log fields keyed by the already-visible `server_request_id`: HTTP status, `failure_category`, `rejected_field`, retryable.

No reconnect, Page reselection, secret rotation, OAuth repetition, provider request, or blind publication is indicated.
