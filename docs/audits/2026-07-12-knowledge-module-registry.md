## Executive Summary

This PR introduces the first Phase 1 foundation for the Knowledge Module architecture: a standalone, metadata-only **Knowledge Module Registry** plus read-only helper functions.

The registry exists so future Brand Workspace work can gradually replace scattered hardcoded module/title/section mappings with a single source of truth. It does **not** integrate with Brand Workspace rendering yet. It is not imported by `app.js`, not loaded by `index.html`, and does not change any existing runtime behavior.

Users should notice no visible change.

## Step 1 — Dependency Audit Findings

### Current Brand Core rendering

Brand Core rendering is currently centralized in `renderBrandCoreTiles()` in `app.js`.

Key dependencies:

- `renderBrandWorkspaceHero()` runs before tile rendering.
- `#brand-core-canvas` is the render owner for grouped Brand Workspace sections.
- Static built-in module cards are generated as `.bc-node[data-bc-key]` elements.
- Existing data keys include `brandCore`, `valueProposition`, `personas`, `messagingPillars`, `toneOfVoice`, `brandAssets`, `keywords`, `contentGuidelines`, `dosAndDonts`, and `brandVoiceExamples`.
- Brand DNA renders separately through `renderBrandDnaCard()` and `#brand-dna-card`.
- Custom cards are removed and recreated on each render.

Dependency risk:

- **High** if this PR modified rendering, because `.bc-node[data-bc-key]` drives editor selection.
- **Low** for a standalone registry file that is not imported or executed by the existing renderer.

Decision:

- Do not refactor `renderBrandCoreTiles()` in this PR.
- Do not replace the current title map or section markup with registry lookups yet.

### Current custom tile rendering

Custom tiles currently live in `state.brandCore.customTiles` and render as `custom:{index}` keys.

Current behavior:

- invalid or malformed generated custom placeholders are skipped by rendering guards.
- canonical Missing Knowledge tiles are visually routed by title into Strategy, Intelligence, or Deployment.
- non-canonical custom tiles render in Custom Knowledge.
- `custom:add` remains the existing add affordance.

Dependency risk:

- **High** if custom tile identity or rendering is changed, because the recent bugfix stabilized `custom:{index}` behavior.
- **Low** for registry metadata that does not read, write, or normalize `state.brandCore.customTiles`.

Decision:

- Do not change custom tile rendering.
- Do not add module IDs to custom tiles.
- Do not migrate custom tile state.

### Current section routing

Current section routing is title-based for missing-knowledge custom tiles:

| Missing knowledge tile | Current visual section |
|---|---|
| Founder Story | Intelligence |
| Market Research | Strategy |
| Business Plan | Strategy |
| Pitch Deck | Deployment |
| Whitepaper | Deployment |

Dependency risk:

- **Medium** because title-based routing is transitional and can be replaced later, but replacing it now could affect visible placement and missing-knowledge behavior.

Decision:

- The registry includes section metadata, but existing routing remains unchanged.
- Future PRs can migrate routing to `getModulesForSection()` after a scoped QA plan.

### Tile creation flow

Current custom tile creation paths:

1. `custom:add` pushes `{ title: "New Custom Tile", content: "", items: [] }`.
2. Missing Knowledge actions call `createOrSelectMissingKnowledgeTile()` and create `{ title: canonicalTitle, content: "", items: [] }` only if a valid matching tile does not already exist.

Dependency risk:

- **High** if creation shape changes, because persistence and editor selection expect the existing custom tile shape.

Decision:

- Do not change tile creation.
- Do not introduce module types or IDs into created tiles in this PR.

### Tile deletion flow

Current deletion path:

- selected `custom:{index}` is validated.
- deletion uses `filter(...)` to remove exactly the selected index.
- selection resets to `brandCore`.
- `saveBrandBrainState()` persists the update.
- tiles and editor rerender.

Dependency risk:

- **High** if identity changes before a backward-compatible ID migration exists.

Decision:

- Do not change deletion behavior.
- Leave stable identity work for a later audited PR.

### Editor loading

The editor is generated by `renderBrandCoreEditor()` based on `state.brandCoreSelectedKey`.

Current editor dependencies:

- built-in modules use keys that correspond directly to `state.brandCore` properties.
- custom modules use `custom:{index}`.
- editor inputs call `saveBrandBrainState()` and rerender tiles/editor as needed.
- Brand Assets editor owns the existing website analysis entry point.

Dependency risk:

- **High** if module registry is wired into editor selection before adapter work.

Decision:

- Do not change editor loading.
- Do not introduce module editor adapters yet.

### Save pipeline

Current save pipeline:

- `saveBrandBrainState()` calls `getBrandCoreData()`.
- `getBrandCoreData()` calls `serializeBrandCoreSnapshot()`.
- `serializeBrandCoreSnapshot()` normalizes and clones `state.brandCore`.
- state is saved to board-scoped local storage and marks the board dirty unless disabled.
- board save flows include `brand_core_snapshot`.

Dependency risk:

- **High** if registry metadata is added to Brand Core state or snapshots.

Decision:

- Registry lives outside Brand Core state.
- Registry is not serialized.
- No save/load/snapshot changes are included.

### Snapshot serialization

Current snapshots serialize existing Brand Core state as `brand_core_snapshot`. Boards list display snapshot logic separately exposes safe `brand_display`, but that is unrelated to module registry metadata.

Dependency risk:

- **High** if module registry metadata is embedded in snapshots prematurely.

Decision:

- Do not change `brand_core_snapshot`.
- Do not add `modules` or `moduleRegistryVersion` to saved data in this PR.

### Custom tile persistence

Custom tiles persist as part of `state.brandCore.customTiles` and retain their current `{ title, content, items }` shape.

Dependency risk:

- **High** for any mutation, migration, or normalization change.

Decision:

- No custom tile persistence change.
- No migration of existing tiles.

## Safest Insertion Point

The safest insertion point is a standalone, unimported registry module:

```text
knowledge-module-registry.js
```

Rationale:

- It is outside `app.js`, so it cannot change Brand Workspace behavior.
- It is not referenced by `index.html`, so it is not loaded in the browser runtime.
- It is CommonJS-compatible, matching the existing Node/API style in the repository.
- It can be syntax-checked independently with `node --check`.
- Future PRs can import or copy selected helpers under a scoped migration plan.

## Rollback Strategy

Rollback is safe and simple:

1. Delete `knowledge-module-registry.js`.
2. Delete `docs/audits/2026-07-12-knowledge-module-registry.md`.
3. No runtime files need to be restored because no runtime files were modified.
4. No storage, snapshot, API, or data rollback is required.

## Why the Registry Exists

The registry exists to centralize module metadata before runtime migration begins.

It provides a single future source for:

- module IDs
- labels
- sections
- descriptions
- default capabilities
- future capabilities
- icon names
- multiplicity rules
- categories

This reduces the risk of scattering title-to-section and module-capability logic across rendering, editor, missing-knowledge, AI, upload, and Knowledge Graph code.

## Current Architecture

Current Brand Workspace architecture remains unchanged:

- Brand Core state is board-scoped.
- Built-in fields are direct `state.brandCore` properties.
- Custom tiles are array entries in `state.brandCore.customTiles`.
- Custom tile identity is still `custom:{index}`.
- Missing Knowledge uses canonical title matching and existing Dashboard knowledge status logic.
- Rendering and editor behavior remain in `app.js`.
- Persistence remains through existing Brand Brain save/load and board snapshot paths.

## Future Architecture

The registry should eventually become the read-only source for module metadata, while runtime state remains separate.

Recommended future layers:

1. **Registry** — static metadata about known module types.
2. **Module instances** — saved user/workspace/board-specific module data.
3. **Renderer adapters** — card rendering based on type and capabilities.
4. **Editor adapters** — module-specific editing UI based on type.
5. **Action registry** — future AI/upload/review actions gated by capabilities.
6. **Persistence adapter** — eventual migration path for typed modules.
7. **Knowledge Graph projection** — reviewed knowledge only.

This PR implements only layer 1.

## Helper Functions

The registry exposes read-only helpers only:

| Helper | Purpose |
|---|---|
| `getModuleDefinition(moduleId)` | Returns one module definition by normalized ID, or `null`. |
| `getModulesForSection(section)` | Returns module definitions for a registry section. |
| `isKnownModule(moduleId)` | Returns whether a module ID is known. |
| `getModuleCategory(moduleId)` | Returns a module category, or `null`. |

These helpers do not read or write Brand Core state.
They do not create modules.
They do not render UI.
They do not persist data.
They do not trigger actions.

## Migration Path

Recommended future adoption sequence:

1. Add registry metadata and helpers. **Completed in this PR.**
2. Add tests for registry helper behavior.
3. Replace hardcoded Missing Knowledge title metadata with registry reads, without changing UI.
4. Replace section metadata in documentation/render constants, without changing DOM output.
5. Add backward-compatible stable custom tile IDs for newly created tiles only.
6. Add optional module type metadata to canonical custom tiles.
7. Extract module card renderer with identical output.
8. Extract module editor adapter with identical output.
9. Add the first typed module MVP after a dedicated audit.
10. Audit uploads, AI actions, and Knowledge Graph projection separately before implementation.
