## Why this spec is needed

Dashboard 2.0 is a strategic product surface, not a homepage redesign. Existing product direction defines the Dashboard as Mission Control: a daily briefing that answers what deserves attention today.

A dedicated implementation spec is needed before runtime work because the Dashboard touches many product areas indirectly: Brand Brain, Boards, Campaigns, Campaign Canvas, Nodes, AI Brain, Knowledge, Insights, Team Activity, and future deployment data. Without a clear ownership model, Dashboard could accidentally become a second Boards view, a lightweight Insights clone, an AI Brain substitute, or a task database.

This audit creates a safe planning artifact that future implementation PRs can reference before changing UI or app behavior.

## Key source principles applied

- Dashboard should answer: "What deserves my attention today?"
- Dashboard orchestrates; it does not calculate canonical product truth.
- Brand Brain owns approved Brand truth.
- Campaign Canvas and Nodes own canvas work and node-level assignments.
- AI Brain advises and owns recommendations/conversation artifacts.
- Insights owns metrics, diagnostics, trends, and evidence-backed observations.
- Knowledge owns imported and curated reusable context.
- Design should reduce cognitive load, feel premium, and make AI collaborative.
- Engineering changes should be additive, audited, small, and low blast radius.

## Why no runtime work was performed

No runtime work was performed because this task is explicitly product and implementation planning only.

The audit intentionally did not modify:

- `app.js`
- `index.html`
- `styles.css`
- API files
- Campaign Canvas
- Campaign V3
- routing
- save/load
- auth
- existing Dashboard behavior

The created files are documentation-only and do not create UI, CSS, routes, business logic, storage, API contracts, analytics assumptions, or app behavior changes.

## Spec produced

Created `docs/product/dashboard-2.0-implementation-spec.md` defining:

- Product intent for Dashboard 2.0 as Mission Control / Morning Briefing.
- A text-based Dashboard 2.0 wireframe.
- Section-by-section data ownership.
- MVP vs Later scope for every Dashboard section.
- Recommendation that Today's Focus should use assigned/open nodes before any separate task system is introduced.
- Brand Avatar voice and behavior principles.
- A safe future implementation sequence.
- Product and engineering risks.
- Final recommendation for the smallest safe first implementation PR.

## How future implementation should reference the spec

Future Dashboard 2.0 implementation PRs should reference `docs/product/dashboard-2.0-implementation-spec.md` before code changes and use it as the scope boundary for what Dashboard may read, display, route to, and modify.

Each implementation PR should confirm:

- Which Dashboard section is being implemented.
- Which owning product object supplies the data.
- Whether data is real, safely derived, or placeholder.
- That Dashboard does not become canonical storage.
- That detailed analytics remain in Insights.
- That strategy conversations remain in AI Brain.
- That board/node work remains in Boards and Campaign Canvas.
- That task-like Dashboard items link back to assigned/open nodes where possible.

## Recommended next implementation PR

The recommended next implementation PR is:

**Dashboard 2.0 static layout / visual structure only, using existing design components and safe placeholders, with no business logic.**

This first PR should avoid APIs, analytics, task storage, deployment assumptions, AI Brain integrations, Brand Brain mutation, Campaign Canvas changes, Campaign V3 changes, save/load changes, auth changes, and routing contract changes.

## Audit conclusion

Dashboard 2.0 should proceed through small, additive implementation PRs only after this planning spec is reviewed. The first implementation should establish the visual hierarchy and information architecture safely, then later PRs can connect individual sections to owned data sources as those ownership contracts become available.
