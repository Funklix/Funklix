## Verified defects and fixes

The old Content route requested `id, name, updated_at`. The real `getBoardAccess` adds `brand_id`, but absent ownership values then satisfy its legacy unowned policy. A projection-aware fixture reproduces unrelated signed access becoming `unowned` with the old projection and denied with actual owner fields. The new route uses a narrow read-only scope owner that explicitly selects and validates both ownership columns before accepting edit access. Missing, malformed and empty ownership fields fail closed. Two actual SQL NULL owner values retain the existing signed unowned Board policy; this PR does not change global role policy.

The route previously checked access once, did not resolve an active application identity or applicable Workspace membership, and did not bind the request to persisted source scope. The new scope owner uses the existing verified-session identity contract and real Board ACL helper in a repeatable-read, read-only transaction with a four-second statement timeout. It checks active identity, active Workspace and accepted recognized membership when the Board has a Workspace, and the persisted Board/Brand/Workspace association using metadata only. Explicit NULL Workspace and Brand associations remain valid legacy cases under existing Board permissions; absent columns cannot stand in for NULL. A legacy associated Brand must match the Board's actual nullable Workspace. Board-only editors need neither canonical Brand read nor edit. Brand viewers with actual Board edit remain allowed; Brand-only viewers cannot edit a Board. No canonical Core, Board snapshot, saved Canvas or Learning content is retrieved for conversion.

The request now requires bounded `expected_scope` with the source's saved `updated_at`, `brand_id` and `workspace_id`. These are equality expectations, not authority. They are compared against persisted data before spending an inference call. Identity/revision, actual ownership and role, Workspace membership/state/revision, association and session actor are captured and revalidated immediately before dispatch and after provider completion. Changed scope produces safe 409; authorization read failure produces safe 503. Initial authentication/access/missing Board failures remain 401/403/404. The Board GET adds only its existing Workspace ID to its read projection so the browser can retain that persisted association; restricted viewer/public serialization remains owned by the existing serializer. Board PUT and its conflict protocol are unchanged.

The existing OpenAI Responses call now explicitly sets `store:false`. Provider/model configuration, strict Content-only schema, field limits, optional-rationale compatibility and EN/DE checks are preserved. Input remains exactly policy plus bounded supplied source text; validated Canvas, account information, catalog, canonical knowledge, snapshots and Learnings are not forwarded. There is one conversion call per explicit Prepare/Retry, with no classifier, repair or automatic retry. Response bytes are streamed with a 65,536-byte ceiling; extracted proposal JSON remains bounded to 6,000 characters and the existing field limits. The 25-second deadline covers both fetch and response-body reading, races stalled transports, aborts the request and cancels the reader. Network/HTTP failures, malformed envelopes/JSON, invalid proposals, language failures and timeout return safe typed errors; raw provider/source/internal strings are neither logged nor displayed.

## Exact browser intent and preserved Canvas workflow

At Advice dispatch the browser captures the account object/email, Board/load, complete local node/edge context plus selection, saved revision and persisted Brand/Workspace association, association generation, and Workspace/catalog identity/generation/state. Only that request's successful turn completes the snapshot with exact turn ID, question and answer. Prepare never recaptures current scope for an old answer. The same original source object and exact text/scope must still match before Prepare, after await and before explicit Create. Native fields beyond the truncated Advice projection also invalidate stale intent. A changed context requires new Advice rather than silently rebasing. Existing account/Board invalidation clears protected conversation state; stale previews are retired without discarding unrelated same-context composer drafts. Delayed success or failure from a cancelled/replaced controller cannot overwrite a newer proposal.

Eligibility rules, supported node type and preview design are unchanged. Prepare performs the existing explicit conversion, Preview remains read-only, Cancel makes no Canvas change, and only Create reaches the existing one-node Canvas adapter. It retains one history snapshot, local IDs/layout/default Draft status, no parent/edge, dirty/autosave signaling, selection/Inspector/reveal, duplicate-ID consumption, and recovery when insertion succeeded before a renderer failed. The existing renderer now retains the composer's selection even when focus has moved to Content controls; it does not steal focus. Local node creation is still distinct from successful server save. No persistence/undo/redo architecture or save-conflict recovery was redesigned.

## Limits and deferred work

Authorization is rechecked at boundaries, not continuously. A later remote permission change still races browser confirmation and the independent Board save; already transmitted provider input cannot be recalled. The legacy Board PUT optional/non-atomic revision contract remains unchanged. Server-side conversion authorizes bounded supplied text but has no durable transcript to attest its historical Advice origin. Random proposal IDs and browser snapshots are not signed capabilities, durable provenance or cross-tab idempotency. Conservative source freshness may require new Advice after catalog or native Canvas changes. Mocked provider tests do not establish semantic truth, live model behavior or actual provider retention configuration beyond the explicit request field.

BW-37.1C-3B remains responsible for broader Content eligibility, exact isolated source extraction, editable source/destination preview and a fresh remote read before Create. BW-37.1C-3C remains responsible for separately verified visual/common-text and Social adapters. No types, Campaign Creator behavior, canonical writes, Learning mutations, new AI calls, schema/migrations, RLS/TLS, production configuration, merge or deployment are included.
