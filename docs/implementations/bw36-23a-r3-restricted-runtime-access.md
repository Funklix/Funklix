## Function, sequence, DDL and trigger dependencies

The four existing protected entry points remain exactly:

- `brand_knowledge_private.write_brand(text,uuid,jsonb,jsonb,boolean)` — preview/Core mutation/receipt; initialization still requires SERIALIZABLE, an empty Core and exact associated Board snapshot.
- `brand_knowledge_private.create_brand(text,uuid,uuid,text,jsonb,uuid)` — authorized Brand creation in the caller transaction, coupled to Board/Project persistence.
- `brand_knowledge_private.lifecycle(text,uuid,jsonb,jsonb)` — authorized logo/delete commands and immutable history.
- `brand_knowledge_private.logo_receipt(text,uuid,uuid,text)` — actor-authorized retry lookup, holding its own Brand row lock.

PostgreSQL requires UPDATE privilege on at least one column for row-locking SELECT, even FOR SHARE. Granting that on `brands` would violate the protected boundary. `tendra_runtime_private.lock_brand(uuid,boolean)` therefore performs only the requested row lock as NOLOGIN `brand_knowledge_owner`, with a fixed `pg_catalog` search path, no dynamic SQL, no returned row or mutation, and a `session_user=tendra_app_runtime` guard. Runtime receives schema USAGE and this function's EXECUTE only. R3 verifies its exact body/owner/configuration and rejects an existing drifted function. The separate owner-owned schema preserves the fingerprint of `brand_knowledge_private` and avoids granting CREATE on `public` to transfer function ownership under Supabase's non-superuser operator.

Brand creation, Project, Campaign and Learning authorization use this lock before a **separate** SELECT so READ COMMITTED reads after a wait see the committed row. Learning/Advisor retain identity/membership/source locks. Logo and nested Advisor reads already hold the Brand lock through `logo_receipt` / Learning authorization; duplicate direct Brand lock clauses are removed. All existing application ACLs remain. A Project creation bug uncovered by real integration testing is fixed: protected functions return JSON timestamp strings while table reads return `Date`; `_project-command.js` normalizes both to the same ISO representation before validating authoritative snapshot provenance.

UUID defaults use `pg_catalog.gen_random_uuid()`; no application serial/identity sequence requires a grant. R3 aborts on an unexpected sequence-backed default rather than granting all sequences. SHA256/digest conversions, JSON/string/date/aggregate builtins and transaction advisory locks use existing PostgreSQL PUBLIC builtin EXECUTE defaults. The verifier explicitly checks UUID, advisory lock, hash and SHA256 execution. No trigger function EXECUTE grant to runtime is needed: PostgreSQL checks it when the operator creates a trigger. Lifecycle/provenance and Workspace last-owner triggers remain installed and owned by their established migration owners. Brand/Board FK and cascade dependencies, Learning immutability triggers and Social composite ownership FKs are exercised against real PostgreSQL.

## Authorization and RLS boundaries

Command-specific permissive policies are addressed only to `brand_knowledge_runtime`. Their USING/WITH CHECK expression restricts the connection identity to `tendra_app_runtime`; a restrictive backend identity policy also covers all 22 tables, including the original Brand SELECT policy. Existing `anon`/`authenticated` restrictive denies remain byte-for-byte unchanged. No browser role inherits the server group, and migration/verification reject any additional member or parent role touching the group/login. Membership must have INHERIT TRUE, SET FALSE, ADMIN FALSE. Neither runtime role may own application tables, create in application schemas, inherit/set an owner, bypass RLS or administer roles.

These policies establish a **trusted server role boundary**, not per-user/tenant ownership. All server rows needed by the workflows are visible to that connection. Verified cookies, canonical identity resolution, explicit Board/Brand/Workspace permissions, account predicates and transaction/row-lock revalidation enforce application user authorization. Protected Brand functions independently check their supplied actor/workspace/membership and mutation contract; the actor email/proof is supplied by the trusted backend. A compromised backend login can exercise its declared server capabilities. RLS does not make an unverified user email trustworthy, and the policy is not advertised as per-user authorization. Separate backend credentials, no browser access and intact handler ACLs are essential.

For `social_token_secrets`, only the one intended backend identity can use these **new** permissions; other roles are not granted the group. Existing separately privileged operators/service identities require private catalog review; R3 does not blindly revoke their established privileges. Encrypted payloads remain encrypted at rest with the server vault key, scoped by account/platform queries and composite FKs. Server-role RLS is not a substitute for those owner predicates or key protection. A read-only impostor-role test and graph checks enforce that new capability inheritance cannot silently be shared.
