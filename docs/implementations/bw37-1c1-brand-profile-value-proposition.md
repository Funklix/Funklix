# BW-37.1C-1 — AI Brain → Brand Profile Value Proposition proposal

Base: latest merged main `1a094fcc0284072773b6c60bedec7122711fa03b`, including #821. Implements the approved [audit, Sections A–K](../audits/bw37-1c-ai-brain-action-handoffs-audit.md). No APIs, migrations, provider requests or persistent objects were added.

## Behavior and ownership

A successful, non-clarification answer can offer **Suggest Brand Update**. All five conversation modes use the same conservative eligibility rule. The original question must request proposed/replacement Value Proposition wording for the Brand/Profile. Campaign-only questions, unlabeled or mixed answers, multiple results, other fields, numeric/performance guarantees and empty/oversized values do not qualify. Supported answer labels are `Proposed Value Proposition`, `Proposed replacement Value Proposition`, `Suggested Value Proposition` (each also allowing `Brand` before `Value Proposition`), and `Vorgeschlagenes Nutzenversprechen` / `Vorgeschlagenes neues Nutzenversprechen`. The colon may be inside or outside balanced Markdown bold around the label. One value line follows inline or on the next nonempty line. A complete pair of straight, English curly, German curly or guillemet quotation marks is removed; the enclosed wording is preserved exactly. A separate single-line `Rationale`, `Begründung`, `Assumption` or `Annahme` paragraph remains supported. `Reasons for Strength` / `Gründe für die Stärke` may instead introduce sequential numbered, single-line reasons. Explanation text stays in the source excerpt and never enters the field value. Competing candidates, unrelated labeled fields, malformed quotes/bold, speculative candidate wording and unsupported structures fail closed. Values are exact, nonempty strings up to 2,000 characters; nothing is silently truncated. This does not require a new Advice response schema or prompt template.

The compact native dialog identifies Workspace/Board/Brand, shows the exact current field representation (including absent/null/blank), an editable suggestion and exact source excerpt. The copy explicitly labels AI wording as a proposal rather than verified fact. Opening, editing, canceling and staging make no persistent write and no inference call. EN/DE copy, existing theme tokens, native modal keyboard/focus/Escape, narrow layouts and zoom are covered.

**Use in Profile draft** opens the existing guided Profile and invokes its destination-owned `stageValueProposition` method. Canonical data establishes the baseline first. The seam accepts only `/brand_core/valueProposition`, checks exact expected value/existence and revision, validates source scope and independently rereads edit authorization. It rejects dirty/manual drafts, pending operations, deferred or unsynchronized state and unresolved website/generation inputs. It never invokes website `applyProposal`/`persistSuggestions`. Duplicate staging and equal-value suggestions are no-ops.

Only a separate deliberate Profile Save invokes the existing `profile_edit`, `canonical-brand-write/v1` command, exact revision/old-value checks, mutation identity, applicable protected review, restricted SQL write/history and authoritative read/reconciliation. Unrelated and unknown Core fields, Founder Story/modules, accepted DNA/Avatar and Board snapshot remain untouched. The excerpt is ephemeral review UI; it is never added as a write-payload provenance field.

For a staged Brain draft, an unchanged name and website retain their exact canonical representation. In particular, URL normalization or a legacy top-level `website` must not introduce an incidental `/brand_core/brandAssets/domain` change during the later Save. Tests assert a one-field command for these representations too.

## Authorization and freshness

The source captures account object/email, Board/load/Canvas identity, Workspace/catalog generation, persisted Brand association and exact successful question/answer. Sidebar Brand Y never retargets Board X. A cached catalog edit role is necessary for the affordance; preparation, staging and source revalidation for Save use fresh authenticated, no-cache reads of `/api/workspaces` and canonical Brand detail. The catalog is the existing read-only owner of persisted Board/Brand/Workspace associations and independent roles; unlike Board-detail GET, it does not enrich editor identity. Missing/revoked membership, active identity, Board edit or canonical Brand edit fails closed without showing current canonical values in the proposal preview.

An old field or revision change requires a fresh comparison. Profile reload retains safe edits but cannot silently authorize a previously staged replacement against a new revision. Reloading an unchanged canonical revision/value preserves the staged comparison and permits the separate Save; the real-shell regression covers this automated-review finding. The existing save contract handles conflicts, failure and exact lost-response retries. Changed canonical state invalidates affected proposals while retaining the conversation. Return to conversation goes through the Profile save/discard/cancel guard and preserves same-Board transcript, composer/caret, mode, disclosure and scroll. Account/Board/load changes clear protected preview state; another account cannot revive a source intent.

## Review and limits

Review focused on owner separation, independent authorization, exact source/baseline capture, no-write staging, cancellation races, safe DOM rendering, preservation of newer drafts, conflict recovery and existing Advice/Content/Profile compatibility. No merge, deployment, production SQL or paid evaluation was performed.

The deterministic format intentionally omits many natural-language suggestions and cannot verify product claims or semantic truth. Humans review the wording before saving. Authorization is rechecked at operation boundaries; it is not continuous revocation. Conversation/source references remain in-memory and disappear on reload. Durable AI provenance, Campaign Creator, Content eligibility expansion, Learnings, tasks and decisions remain deferred. Existing generation/proposal transport gaps documented in the audit are unchanged and are not inherited by this zero-inference bridge.

## BW-37.1C-1R1 eligibility correction

Base: merged main `1cb43729d8b81900eeed4aa0e1e9d03f71d8795a`, including PR #822. The production `aiBrainValueProposition` regex rejected the exact Appics DEMO 2 reply for three independent format reasons: the extra `Brand` in the label, a heading followed by a blank line and quoted value instead of an inline value, and the separate numbered `Reasons for Strength` section. Merely adding `Brand` to the old regex would not resolve that reply. The existing bold matcher also did not safely handle the colon-inside-bold heading as a separate heading. The supplied question already passes the request-intent gate. This reproduction establishes an extraction blocker; it does not prove the live user's cached roles or source freshness.

The fix changes only deterministic extraction, this documentation and the existing `check:bw37.1c1` suite (already included in Runtime Boot Safety for PostgreSQL 17.6 and 18.4). The regression uses the exact supplied question, quoted proposal and reason headings/ellipses. It checks the exact extracted value and full source excerpt, balanced EN/DE label/quote variations, old inline rationale formats, ambiguity/claim/strategy negatives, and the real shell's authorized CTA, excluded explanation, editable preview, cancel, zero-write staging, separate protected Save and missing canonical authorization. Existing security, lifecycle, knowledge-preservation and responsive UI cases remain in that suite.

All independent authorization, persisted association, account/source/load identity, revision/old-value matching and destination-owned staging/Save code is unchanged. No Advice contract, model call, UI, infrastructure or database change is introduced. The bounded parser cannot verify the truth of the Appics reward/income claims; wording remains an unverified proposal for human review. Unlabeled prose, multiline values, arbitrary Markdown and unrecognized explanation formats intentionally remain unsupported.

Codex review identified a missing-value edge case: a proposal heading followed directly by `Rationale: …` could be mistaken for wording. The extractor now rejects recognized explanation labels as candidate values, with deterministic missing-value regressions for all supported EN/DE explanation labels (inline or after a heading). Whitespace-only quoted values are also rejected.
