# BW-35.3R5 Auto-plan production evidence

## Actual failing stage

The failure occurred **before browser dispatch**. `renderCore` built the calendar authority with
`requestLifecycleGeneration || accessGeneration`. The initial publishing lifecycle is the valid
number `0`, so the truthy fallback replaced it with the Board-load generation. Apply then passed
that substituted generation to `dispatchAutomaticPlanningBatch`, whose first guard compared it to
the still-zero publishing lifecycle and returned `BOARD_CHANGED`. No HTTP request was made.
`applyAutomaticPlanning` received a result with no failure category; its final fallback selected
“The plan could not be applied.”

This accounts for the observed pending transition, generic message, and absence of persisted
schedules without requiring a route, authentication, contract, or database failure.

## Repair and bounded diagnostics

The snapshot now uses nullish fallback, preserving lifecycle generation `0`. The Apply boundary
creates one bounded `req_autoplan_…` ID and dispatch reuses it for the header and body. The route
returns JSON failures with allowlisted `code`, `stage`, and `request_id` fields while retaining the
existing authoritative response contract. Diagnostics cover route entry, authentication, contract
acceptance/rejection, database-adapter load, service entry, transaction start, Board lock, command
validation, commit, and rollback.
