# BW-26.3 pre-implementation audit

The audit was performed against merged BW-26.2 (`16d860d`) before implementation.

1. **Turn lifecycle.** Browser-only `state.aiBrain` owns a sequential `messages` transcript, a single active request/controller, request generation, identity, and aggregate status. A submitted question creates one pending turn; success adds the answer and metadata; failure leaves the question as a retryable failed turn.
2. **Existing request.** `POST /api/ai-brain/advice` sent exactly `board_id`, `question`, `selected_node_id`, `canvas_context`, and `response_language`, plus the `X-AI-Brain-Generation` header. It sent no transcript data.
3. **States.** Turns explicitly use `pending`, `success`, and `failed`. Aborted and stale responses are discarded by abort/request-generation checks rather than retained as turn states. Failed turns are the retriable state. Aggregate request state uses `idle`, `loading`, `success`, and `error`.
4. **Retry.** Retry finds the same failed turn by ID, preserves its question and position, clears its old failure/answer, changes it back to pending, and sends it with the current Canvas and selection. It does not append a duplicate turn.
5. **Text limits.** The composer and server bound a current question to 2,000 characters. Provider output is normalized to at most 12,000 characters.
6. **Request/Canvas budgets.** The complete JSON request is capped at 350,000 UTF-8 bytes. Canvas validation additionally caps 200 nodes, 400 edges, IDs at 160 characters, short node fields at 1,000, content at 8,000, nested fields at 3,000, and hashtags at 20 items of 100 characters.
7. **Provider messages.** The route constructs one system instruction followed by one user message containing the current question and the freshly authorized Board/Brand/Canvas/diagnostic context.
8. **Injection boundary.** Canvas and question content are user-provided data under the system instruction; model output is untrusted and rendered through a restricted `textContent`-only formatter. The server, not the browser, resolves Board and optional Canonical Brand authorization.
9. **Invalidation.** Account, Board, and Board-load generation form the conversation identity. Access, selected node, Canvas nodes/edges, and identity form the in-flight context identity; changes abort, discard, or fail the affected request. UI language determines each request's response language. Leaving the AI Brain view alone does not clear memory, while an account/Board/load identity change does.
10. **Clearing.** `invalidateAiBrainRequest` aborts the active fetch and replaces all messages with an empty array. Board/account/load changes invoke this through identity checks and Board lifecycle paths. Nothing writes the transcript to a database, `localStorage`, or `sessionStorage`.
11. **Regression coverage.** BW-26 checks authentication, editor-only access, server-resolved context, read-only behavior, timeout, and surface wiring. BW-26.1 covers real Canvas projection/validation, size limits, stale selection/edges, retry de-duplication, abort/stale-generation rejection, and provider gating. BW-26.2 covers safe bounded response parsing/rendering, English/German assumptions labels, responsive wrapping, and lifecycle regression assertions.

## Confirmed gap

Previous answers were unavailable because `state.aiBrain.messages` was used only to render the transcript. The request serializer sent only the five current-turn/context fields, and the server provider input contained only the system message plus the current question and authorized context. No previous successful question/answer pair crossed either boundary.
