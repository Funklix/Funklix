# BW-33.3R1 — post-hydration Canvas density recovery

Density is a passive Canvas presentation preference. The exact browser key is
`tendra.canvasDensity.v1`, with `{ "version": 1, "mode": "compact" | "standard" | "detailed" }`.
Missing, malformed, invalid, or unreadable values resolve to Compact. A failed write retains the
selection in memory for the session. No Board, user, node, content, or workspace identifier is
stored.

The sole activation boundary is the zero-delay task scheduled at the successful end of
`loadBoardFromUrlIfPresent`, after the authoritative response was accepted, access applied,
`applyCampaignState` returned, nodes rendered, the active Board ID was established, and the normal
Canvas owners started. Because it is a separate task, boot completes its Canvas/Inspector pass and
density failures cannot enter the loader's access-error catch. Stale, pending, failed, malformed,
logged-out, Home, and Boards states do not activate it.

The marker is `#canvas[data-tendra-canvas-density]`. Compact hides only established secondary
Canvas-node descendants (body copy, expand affordance, images, tags, A/B material, social preview,
and compact summary); role, title, status/warning descendants, node actions, approval/review state,
and connection controls remain. Standard bounds existing body preview and hides images/A/B
material. Detailed adds no hiding and is the unchanged presentation. Unclassified descendants are
deliberately left visible. Inspector, Content Workspace, shell, library, dialogs, auth, node data,
geometry, persistence, history, autosave, collaboration, approval, and publishing are untouched.

`check:bw33.3r1` executes the production preference module and the actual production activation and
application functions in a deterministic browser-runtime shell. It covers pre-hydration inertia,
post-hydration ordering, reload preference, exact marker scope, data equivalence, and injected read,
write, marker, menu, and redraw failures. This is not claimed as full real-browser coverage. The
historical failure was established by BW-33.3A; the permanent CI regression uses a minimal committed
deterministic representation of its unsafe pre-session activation, renderer coupling, and escaped
access-classification failure. Production behavior is tested directly from the current checkout,
and the regression requires no Git history, reflog, or unreachable object availability.

## Production verification gate

After deployment: (1) sign in with Google; (2) open an existing private Board from Boards; (3)
confirm nodes and Inspector load; (4) switch Compact, Standard, and Detailed; (5) return to Boards;
(6) open a second existing private Board; (7) reload the browser; (8) confirm the Board remains
accessible. Automated lifecycle coverage must pass before review, and this sequence remains required
for final production confirmation.
