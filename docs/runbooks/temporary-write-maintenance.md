# BW-36.23A temporary write maintenance

This is an application write gate for the production PostgreSQL migration window. It introduces no database DDL, migration changes, credential changes, or data updates. The implementation is `api/_write-maintenance.js`; `TENDRA_WRITE_MAINTENANCE` is its only switch. Missing/`0`/`false` disables it; `1`, `true`, or `on` enables it (case insensitive, whitespace trimmed). Use exactly `1` and `0` operationally. Never use a `NEXT_PUBLIC_` variable or a browser control.

## Behavior and coverage

The shared `api/_boards-storage.js` pool is the only application `pg` entry point. Its pool and acquired clients (promise and callback APIs) check every query immediately before dispatch, including work outside an HTTP request. Maintenance rejects DML, DDL, writable CTEs, multi-statement queries, session changes, unreviewed SQL functions and stored mutation functions. Existing read SQL and audited read-only/lock helpers remain available. Exact `write_brand` preview invocations with boolean `preview=true` and `logo_receipt` reads remain available; actual writes and lifecycle/create calls do not. This is a bounded application gate for the audited SQL inventory, not a general-purpose SQL parser or a substitute for database privileges. New functions/SQL require maintenance-test review.

Every database-dependent HTTP handler retains its original authentication and authorization and adds a common response boundary. A blocked query marks only that request via AsyncLocalStorage. Even handlers that catch/translate errors or redirect OAuth callbacks return HTTP **503**, `Retry-After: 60`, `Cache-Control: private, no-store`, and JSON with `code: TENDRA_WRITE_MAINTENANCE`, `retryable: true`, and:

> Database writes are temporarily paused for maintenance. Please retry after maintenance ends.

Sixty seconds is retry guidance, not a promise that migration will finish then. Invalid/unauthorized requests can still receive their existing validation/auth errors. A replay that only reads an already committed outcome can still succeed. Authentication cookies and ordinary reads are not disabled. The UI may show an existing generic error; the server response always carries the retry message. No client rollout is needed to enforce the gate.

Board GET skips optional editor-identity enrichment. LinkedIn/Facebook job/publication reads skip optional delivered-state repair and accepted-attempt reconciliation; they return stored state, which can remain stale until maintenance ends. No provider publish is retried by a status read. Pure POST reads (preflight, AI analysis, source/knowledge preview) remain available where they perform only read queries. Logo mutations explicitly stop before uploading/deleting assets. Disabled document-import mutations report the maintenance retry contract after authorization; they do not reactivate ingestion.

`vercel.json` contains no cron definitions; no independent scheduler/queue consumer is declared in this repository. Document jobs are explicitly driven through the authenticated worker route; Social delivery/finalization runs within publishing services. Any externally configured scheduler, queue runner, retry service, integration or standalone script is an operator inventory item: it must use this guarded revision and flag, or be paused. Direct SQL clients, other applications and old code are outside this gate. CLI migration/verifier scripts intentionally remain operator-controlled and are not runtime entry points.

The regression test discovers all 54 transitively database-dependent HTTP handlers and enforces their response wrapper. It executes all current literal application query sites through a guarded fake pool and client: 116 mutating sites are rejected before dispatch and 137 read sites pass; dynamic SQL helpers still dispatch through the same guarded pool. It also exercises real Board/member/Workspace/Project/Learning/Document handler control flow, both OAuth GET callbacks, document cleanup/scanner work, Social reconciliation suppression, concurrent request isolation, authentication/authorization responses, callback APIs, previews and reversal. It makes no database or provider calls.

## Operator preparation (no actions are performed by this PR)

1. Review and merge this PR through the normal process. Record the resulting Git commit SHA containing the gate; do not use an older revision. Complete Runtime Boot Safety for that revision. Record the current production deployment ID, domains/aliases and source SHA for recovery.
2. In the **actual Vercel project** hosting production, inventory every deployment/branch/preview URL, custom domain, external worker and other process that can use the production PostgreSQL credentials. Include deployment-specific URLs, aliases, cron/webhook targets and automation bypass access. Preview deployments that use isolated databases need not be gated for this production migration; ones that share production must be gated or made inaccessible.
3. Record each function's effective maximum execution duration and each external worker's maximum lease/execution duration. `vercel.json` explicitly sets Learning Advisor to 300 seconds; other routes inherit effective Vercel/project/plan settings, so **300 seconds is not a proven global drain time**. Include DB query/transaction timeouts and any detached work. If a writer has no proven upper bound, use logs/job telemetry to prove completion or cancel it through its normal operational controls before proceeding.
4. Pause external job dispatch/retries, publishing integrations and webhooks that could target old deployments. A failed/503 OAuth flow must be restarted after maintenance; do not replay an old authorization code. Preserve job IDs, idempotency keys and attempt state for later reconciliation. Do not create a second publish request when provider acceptance is ambiguous.

## Activate on Vercel

1. Open **Vercel Dashboard → production project → Settings → Environment Variables**. Add/edit **`TENDRA_WRITE_MAINTENANCE` = `1`**, selecting **Production**, then **Save**. If any other environment uses production credentials, set the same value for that environment (including branch-specific overrides), or isolate that deployment from requests/workers. An environment edit alone does **not** change any running deployment.
2. Open **Deployments**. Select a deployment built from the recorded gate-containing SHA, select **… → Redeploy**, use the Production environment, and confirm that the new deployment uses the saved environment variables. Wait for **Ready**, verify its source SHA/environment, and ensure it is the deployment serving all production aliases. If redeploying an older deployment would use a pre-gate SHA, stop: create the deployment from the reviewed gate revision through the normal release process instead. This PR itself does not deploy anything.
3. For every other reachable deployment with production DB access, either redeploy the gate revision with `1` in its own environment, or prevent all further calls to that deployment. To retire an old deployment, use **Deployments → select the old deployment → … → Delete** after recording its source/configuration for a future fresh redeploy. Removing a production alias alone is insufficient: the old unique deployment URL can remain callable. Deployment Protection is sufficient only if its rules actually deny every caller, including integrations and bypass tokens; prove this for every old URL. Do not rely on protecting anonymous traffic alone. Do not leave an old writable deployment available for rollback during the window.
4. Verify the **new unique deployment URL and each production domain** using an authenticated, valid mutation against a disposable test resource: expect 503, code `TENDRA_WRITE_MAINTENANCE`, the retry message and `Retry-After: 60`. Use an existing test resource and the normal authenticated request shape. Do not submit real Social publishing or SQL as a probe. Verify Board/Brand/Workspace/Learning/Document metadata and Social settings/status GETs still read successfully with the same authorized account. Unauthorized requests must retain their existing denial and reveal no data. Verify retired URLs cannot invoke the old API.
5. Start the drain interval only **after the last ungated writer stops receiving new work**. Requests that already dispatched SQL on old deployments may still commit. Redeploying or changing aliases does not cancel their transactions, provider requests, background promises, or leases. Wait at least the longest verified remaining function/worker/query duration, and verify in Vercel Runtime Logs plus external job telemetry that all old invocations, transactions and provider attempts have finished or been deliberately stopped. Application logs alone cannot prove that a separate direct SQL client is idle; coordinate those writers with their owners. Do not run the migration while any old/in-flight writer is unresolved.
6. Keep `1` active and job dispatch paused throughout the separately approved migration and verification. A new deployment from a different SHA/environment may reopen writes: freeze releases or verify every replacement deployment has this gate enabled. Never promote/roll back to an old deployment to recover during the maintenance window.

## Deactivate on Vercel

1. After the migration owner confirms completion and verification, keep dispatch paused. In **Settings → Environment Variables**, change **`TENDRA_WRITE_MAINTENANCE` to `0`** for Production and each other affected environment/branch override, then **Save**. Removing the variable also disables the gate, but `0` is explicit.
2. In **Deployments**, redeploy the same reviewed, migration-compatible gate revision with the updated environment. Wait for **Ready**, verify the source SHA and aliases, and verify that authorized reads work and an approved test-resource mutation succeeds. The deployment with `1` continues rejecting writes until replaced; do not assume editing the variable updates it. Do not restore a pre-migration deployment with incompatible code/configuration.
3. Re-enable dispatch/retries gradually. Reconcile already accepted Social provider attempts using their existing job IDs/status and normal recovery flow before allowing a new publish. Resume document leases/jobs through their existing retry controls if applicable; document ingestion remains disabled by its existing feature switch. Do not clear idempotency receipts or rewrite job data.
4. If reopening causes problems, set `1` and redeploy the compatible gate revision again, then repeat the old-deployment isolation and drain checks. Removing the temporary gate code later is a separate reviewed change; no database rollback or DDL is needed merely to toggle this mechanism.

**Migration go/no-go:** gate revision + flag verified on every accessible writer; old deployments inaccessible; dispatch paused; all in-flight writers drained; authorized reads verified. If any item cannot be demonstrated, keep maintenance active and postpone the migration. A Vercel environment variable is deployment-scoped, not an instantaneous fleet-wide kill switch.
