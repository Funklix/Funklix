## Finding and attribution limit

This is a diagnostic improvement and a verified provider-error rejection fix,
**not a claim that the second Appics incident has been repaired**. No production
log source, production database, or OpenAI credential binding was available.
No private Appics data or paid inference was accessed.

The reported English message is produced by the #840 browser mapping for four
server reasons: `json`, `schema`, `envelope`, and `size`. It does not distinguish
malformed provider envelopes, invalid model JSON, schema violations, or excessive
response size. It does not, by itself, establish token exhaustion, refusal,
incorrect citations, or an unsupported model. Incomplete responses and refusals
have separate messages. The missing evidence cards follow from rejecting the
response before source resolution; absence of cards is not a separate diagnosis.

PR #840 already fixes the empty aggregate fallback. That case succeeds on the
required baseline and is not presented again as the root cause of this incident.

One separate defect is reproduced on the actual Advice route: a response carrying
`error: {code: 'server_error'}` and otherwise valid text with `status: completed`
returns HTTP 200 and releases a saved-source card. The failing pre-change
assertion was `actual: 200, expected: 502`. The parser never checked `error`.
It now rejects non-null provider errors and failed status as `provider_error`.
This defensive inconsistent-envelope case is not evidence that the production
provider emitted such a response, or that it caused the reported format error.

## Production pipeline

1. `app.js/requestAiBrainAdvice` captures the explicit mode, response language,
   Board/Brand/Workspace identity, Canvas revision and bounded working projection.
   It submits one `/api/ai-brain/advice` request. Switching mode does not infer.
2. `api/ai-brain/advice.js` validates request keys/size, signed session, editable
   Board authorization, working nodes and selection. Canonical Brand access is
   checked independently. Workspace membership alone never grants Board/Brand
   authority.
3. `_ai-brain-evidence.js` builds exact 180-character quote prefixes for at most
   24 nodes, bounded by 32,000 serialized characters. `_ai-brain-goal-context.js`
   captures saved scope and goal provenance even when goals are absent.
   `_ai-brain-learning-context.js` captures separately authorized Learnings and
   token-counts the complete message set. Partial coverage cannot prove absence.
4. System instructions require the exact answer/findings envelope and source
   quotations. The Responses request uses the configured model (default
   `gpt-4o-mini`), `store:false`, 4,096 output tokens, and existing input/framing
   accounting. It has no `text.format`, tools, classifier, repair call or retry.
   Existing pre-inference context revalidation remains.
5. Non-2xx provider HTTP, fetch failure and abort now emit distinct safe request
   stage diagnostics. Invalid outer response JSON becomes `envelope`; provider
   response status, incomplete details and refusal content are checked before
   accepting model JSON. Provider error messages are never copied into logs.
6. `_ai-brain-social-evidence.js/inspect` uses a nonempty aggregate or joins all
   assistant output-text blocks in order. Reasoning, tool and refusal text never
   becomes answer text. Nonempty malformed aggregates remain authoritative;
   no text repair, truncation or partial-object salvage occurs.
7. Whole-response JSON and strict server schema validation precede finding
   extraction. Exact object keys, string limits, at most three findings, and one
   or two citations are unchanged. Schema failures now distinguish envelope
   keys, answer, findings, individual finding and citation structure.
8. Existing post-inference Learnings and saved-scope freshness checks still run
   before invalid-envelope feedback or any released answer. Language mismatch
   retains its own code. Unsupported shape never reaches source resolution.
9. `resolve` checks exact authorized saved Social node identity/type, allowed
   fields, identical indexed quotes, positive non-goal first evidence and optional
   same-node goal. Saved/working state compares full supplied values with the
   saved baseline, with field-specific goal handling. Semantic absence/count/
   performance guards remain conservative. Unverifiable assertions are omitted;
   matched source text does not verify the AI interpretation.
10. The route serializes natural answer, verified findings, bounded scope
    references and omission counts. New source-stage logs contain counts only.
    A valid empty array, including all citations omitted, remains HTTP 200.
11. The browser checks response language, current request/Canvas identity and
    evidence contract, then renders text safely and bounds cards. Changed context
    invalidates references. Provider errors now receive concise EN/DE feedback;
    schema/JSON failures retain the existing format message.
12. Open in Canvas calls `evidence-reference.js`, independently reauthorizes and
    compares saved source revisions twice, then selects the exact ID and opens
    the normal Inspector. It does not infer or write Canvas/Brand content.

The single Advice invalid-envelope return is the source of the public
`evidence_response_invalid` code. `app.js` maps its reasons to localized errors;
the locale dictionary contains the unusable-format string. No other producer of
that exact message was found. Transport/context/language errors and a successful
empty evidence list use distinct paths.

## Minimal diagnostics

Existing `AI_BRAIN_EVIDENCE_REJECTED` metadata is retained: allowlisted reason,
provider status, incomplete reason, numeric output token count, output character
count and reserved output tokens. Added fields are:

- Stage: `provider_request`, `provider_response`, `envelope_validation`.
- Observed provider completion boolean; it is not inferred from token usage.
- Text presence; output/content block counts and allowlisted block types.
  Unknown types become `other`; arbitrary provider type strings are not logged.
- Allowlisted JSON/schema validation category and accepted finding count.
- Safe HTTP status for non-2xx responses; no provider body/message.

`AI_BRAIN_EVIDENCE_VALIDATED` logs only `source_validation` and numeric candidate,
verified and omitted finding counts. It distinguishes a legitimate zero-finding
answer from rejected output and from unverifiable citations.

No prompts, questions, output bodies, excerpts, Brand/Canvas content, node titles,
node/user/Board identifiers, credentials or arbitrary provider errors enter these
events. Existing authorization/context errors remain their existing public codes.
Platform request logs can associate these events with a request without adding
private identifiers. New tests inject private sentinel strings and check redaction.

## Provider/API contract

The current request is valid Responses API plain-text usage. It does **not**
activate provider-enforced JSON or schema output; prompt instructions alone do
not guarantee a schema-conforming response. The configured model can also be an
administrator override; its actual deployed value is unavailable here.

The official SDK defines Responses structured output under `text.format`, using
`type: json_schema`, `name`, `schema` and `strict: true`. It explicitly documents
the default as plain text. SDK definitions were inspected without an inference:

- https://github.com/openai/openai-python/blob/main/src/openai/types/responses/response_text_config_param.py
- https://github.com/openai/openai-python/blob/main/src/openai/types/responses/response_format_text_json_schema_config_param.py
- https://developers.openai.com/api/docs/guides/structured-outputs

The repository's existing Learning Advisor uses a strict Responses schema with
the same default model. A narrow future evidence schema could close every object,
require all current fields and use arrays for findings/evidence; server length,
card-count, authorization, quote and provenance validation must still apply.
Strict output does not remove refusal, incomplete-output or source-validation
outcomes. No model-contract change is made here: we have neither production logs
establishing a model formatting cause nor provider acceptance evidence for a new
contract on the actual deployed model. Mock transport cannot prove that.
